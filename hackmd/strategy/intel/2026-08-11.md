## 3) Strategic Prioritization (Impact vs Risk, Dependencies, Resource Allocation)

### Priority stack (next 7–14 days)

#### A) Restore first-run reliability (Owner: Cloud/Infra)
1) **Provisioning failure regression (#18052)** — highest user impact  
   - Goal metrics:
     - Failure rate **<1% rolling 7d**
     - User notification on failure path **<3 minutes** (replace ~52 min watchdog experience)
   - Likely dependency chain (from issue hypotheses):
     - Fleet capacity accounting (#17866) → placement funnel/outage history (#17880)
     - Autoscaler ceiling bug (hardcoded maxNodes=12 vs 14 enabled) → no pre-warm
     - Fence deadlock / 409 enqueue refusal (#17924) + daemon pinned behind `main`
   - Recommendation:
     - **2-engineer “tiger team”** for 72 hours: one on autoscaler/capacity, one on fence lifecycle + prod daemon deployment alignment.
     - Ship **fast fail + clear UI messaging** immediately even before root cause fully resolved.

2) **Auth providers endpoint latency (#18049)** — conversion blocker  
   - Recommendation:
     - Treat provider list as **cacheable config** (explicit TTL + explicit invalidation on deploy).
     - Add p95 SLO and alerting for `/steward/auth/providers`.  
   - Target: **p95 <300ms in prod** (per issue acceptance).

#### B) Fix “false green” quality signals (Owner: CI/Release)
3) **Staging lane proof (#18076)**  
   - Recommendation:
     - Split jobs: prod vs staging with **asserted base URLs** and **separate credentials**.
     - Fail-closed if host mismatch (prevents accidental prod coverage masquerading as staging).

#### C) Reduce connector onboarding friction (Owner: Connectors/Gateway)
4) **Telegram onboarding binding (#17888)**  
   - Recommendation:
     - Ensure canonical onboarding URL points to a **known-good host** (avoid `eliza.app` waitlist artifact conflicts).
     - Complete **server-validated Telegram proof** before linking identity; add E2E tests for replay/mismatch/expiry.

#### D) Convert wins into adoption (Owner: DevRel/Docs)
5) **Transportation agent write-up**

## Cross-cutting risk & mitigation

### Risk: Narrative fragmentation (token vs OSS)
- Discord shows continued token trading/integration expectations despite internal pivot.
- Mitigation (low engineering cost, high trust impact):
  - Publish a **single canonical “Token status & governance FAQ”** and pin it (Discord + website + GitHub discussion).
  - Explicitly answer:
    - token status (support/no support), exchange listings are not roadmap
    - who controls what today (or “unknown; investigating” with owner + date)
    - what users should evaluate instead (OSS milestones, cloud reliability, connectors)

### Risk: Shipping velocity masking user-visible blockers
- High merged PR volume can still produce user perception of “no progress” if first-run onboarding is unreliable and login is slow.
- Mitigation:
  - Rebalance roadmap communication toward **3 user-facing reliability metrics** (login TTI, provisioning success rate, connector onboarding completion rate) and report weekly.

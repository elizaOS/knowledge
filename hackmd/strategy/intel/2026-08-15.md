### 3) Strategic Prioritization (Impact vs Risk, Dependencies, Resourcing)

#### Priority A — Trust & Narrative Reset (User impact: Very High | Tech risk: Low)
**Problem:** Token-era confusion is still the dominant lens; it suppresses product adoption and makes recruiting harder.  
**Action:** Publish a short, immutable “State of the Project” that clearly separates:
- token status (ended),
- brand ownership/governance facts (what is controlled by whom),
- product roadmap (web2 consumer + agent infra),
- and a “what we can/can’t help with” section (migration window, foundation, etc.).

**Dependency:** None (comms-only).  
**Resourcing:** 1 owner + 1 reviewer; ship within 48 hours.

#### Priority B — Onboarding + Auth Performance (User impact: High | Tech risk: Medium)
**Problem:** Sign-in time-to-action and onboarding binding issues are the first-session drop-off multipliers.  
**Known critical UX risks (from open issues):**
- **Login gating latency**: `/steward/auth/providers` can block sign-in buttons for up to **4.7s** in production.
- **Staging vs prod proof gaps**: CI can appear green while actually testing production defaults (coverage illusion).
- Telegram identity binding historically unreliable; confusion persists.

**Action:** Treat “time-to-first-action” as a P0 product metric:
- cache or static-serve auth provider list with explicit invalidation semantics,
- enforce environment assertions (staging must prove staging),
- add a minimal E2E “connector identity binding” test for Telegram/Discord onboarding continuations.

**Dependency:** Cloud/Worker + UI coordination; requires secrets/CI environment hygiene.  
**Resourcing:** 1 platform engineer + 1 QA/CI owner for 1 week.

#### Priority C — Provisioning Reliability Regression (User impact: High | Tech risk: High)
**Problem:** Reported **16.1% provisioning failure** after a dated regression; failure path takes ~**52 minutes** to surface and can cause permanent lockouts until fixes land.  
**Action:** Make provisioning reliability the operational critical path:
- isolate root cause among capacity/autoscaler limits/fence deadlock,
- shorten failure notification path (hard timeout + actionable error),
- ensure prod daemon is not pinned behind main fixes.

**Dependency:** Fleet capacity, autoscaler config, job/fence lifecycle correctness.  
**Resourcing:** 1 infra owner + 1 oncall rotation for 1–2 weeks until <1% rolling failures.

#### Priority D — Builder Conversion Loop (User impact: Medium | Tech risk: Low)
**Problem:** Builders show up, but there’s no consistent “next step.”  
**Action:** Add a “Welcome Builder” automation:
- auto-reply with 3 curated starter tracks (MCP server, plugin template, workflow studio examples),
- assign a “builder triage” volunteer weekly,
- create a public “Integrations Wanted” list (payments/DAO, EVM analytics, MCP datasets).

**Dependency:** Minimal (Discord ops).  
**Resourcing:** Community lead + 1 engineer to maintain starter list.

# 3) Strategic Prioritization (Impact × Risk × Dependencies)

## P0 — Contain reputational/legal drag (this week)
**Initiative:** Publish an explicit “Token is dead / what we will and won’t do” closure page + remove official token references.  
- **User impact:** Very high (stops recurring confusion, reduces conflict).
- **Technical risk:** Low.
- **Org/legal risk:** High if mishandled; requires careful wording.
- **Dependencies:** Legal review; comms owner; update permissions across X, docs, Discord pinned posts.

**Recommendations**
1. **Single canonical closure statement** (website + pinned Discord + GitHub org discussion) with:
   - Final status, foundation wind-down facts, and a clear “no roadmap / no buybacks / no support” line.
   - “Software continues” separation statement.
   - A short FAQ for holders (“what should I do?”) that avoids financial advice but provides clarity.
2. **Artifact cleanup sprint (24–48h):**
   - Remove token links from: docs, Discord channel descriptions/pins, X bio/links, partner materials.
   - Add redirects or “deprecated” banners if removal breaks historical references.
3. **Moderation policy change:** Explicitly route token talk to a quarantined channel (or disallow entirely) with automated enforcement; keep core channels technical.

## P1 — Re-anchor the community around building (next 2 weeks)
**Initiative:** “Builder community reset” without nuking history.  
- **User impact:** High (improves retention of serious contributors).
- **Risk:** Medium (backlash if perceived as censorship).
- **Dependencies:** Moderator capacity, clear rules, and consistent enforcement.

**Recommendations**
- Introduce a **server charter**: what ElizaOS is now (open-source agent runtime + apps), what it is not (token project).
- Add a **“Start Here (Builders)”** flow: links to contribution skill/leaderboard, good-first-issues, core roadmap, and “how to ship an agent that generates revenue” (aligning with Shaw’s guidance).

## P2 — Product roadmap: prove “normal user” value (next 4–8 weeks)
**Initiative:** Focus on 1–2 flagship “normal user” agents with measurable utility.  
- **User impact:** High if shipped; converts sentiment into adoption.
- **Technical risk:** Medium (scope creep).
- **Dependencies:** Clear target persona, UX design, metrics definition.

**Recommended focus choice (based on demand + feasibility)**
- **Research assistant with document integration** (high utility, aligns with existing documents/providers work; easier to validate).
- Optionally, **health/fitness tracking** as a second lane if partnerships (phone/OS) are real and near-term.

**Success metrics (must be defined before build)**
- Activation: time-to-first-successful task
- Retention: 7-day repeat usage
- Reliability: tool failure rate and “honest failure” quality (already a code focus)
- Monetization readiness: ability to demonstrate value without a token (subscriptions/hosted inference/app marketplace, etc.)

## P3 — Specialized Web3/DeFi capabilities (selective, opt-in)
**Initiative:** Support Web3 agent tooling as “hidden plumbing” + ensure auditability patterns for finance.  
- **User impact:** Medium (subset).
- **Risk:** Medium–High (regulatory optics, complexity).
- **Dependencies:** Clear UX abstraction + logging/trace standards.

**Recommendation**
- If DeFi calculators are kept: require **deterministic traces** (reproducible steps + inputs + versioned formulas) as an optional “audit mode,” not a default UX burden.

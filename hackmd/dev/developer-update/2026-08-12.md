### Production promotions and release mechanics
- **Develop → Main promotions** shipped large batches of fixes and operational hardening to `api.elizacloud.ai` and `app.elizacloud.ai`:
  - Release promotion: **#17865** “billing fix, app-mode onboarding, sso, voice parity (+448 commits)”

These promotions matter to framework builders because a number of runtime contracts (planner/evaluator, addressing gates, connector identity binding, voice turn persistence) changed behavior in subtle but user-visible ways.

### Planner/evaluator contract tightening (core runtime)
- **Turn-scope declaration is now required on planner tool calls**: **#18247**  
  https://github.com/elizaos/eliza/pull/18247  
  If you author custom tools or a custom planner delegate, ensure you emit an explicit `eliza_turn_scope` (see “Breaking Changes” for migration guidance).

- **Planner budget fixes for reasoning models** (prevents “required tool call never emitted” when completion budget is consumed by reasoning deltas): **#17630**  
  https://github.com/elizaos/eliza/pull/17630

### Provider execution and latency stabilization
- **Cancellation-safe provider deadlines** (prevents timeouts from being cached as “empty context” and avoids runaway work after a timeout): **#17490**  
  https://github.com/elizaos/eliza/pull/17490
- **Prompt cache reuse improvements** (reorders Stage-1 prompt to maximize prefix caching on providers like Cerebras): **#17515**  
  https://github.com/elizaos/eliza/pull/17515

### Security boundaries (core + cloud)
- **Cloud A2A boundary now rejects caller-authored `system` messages**: **#17643**  
  https://github.com/elizaos/eliza/pull/17643  
  This is a critical architecture hardening: “system policy” must be server-owned, not caller-supplied.

- **Never echo the external-content security envelope into chat**: **#17629**  
  https://github.com/elizaos/eliza/pull/17629  
  If your plugins/actions historically used `message.content.text` without considering envelope wrapping, this removes a class of accidental leakage into downstream tool queries.

## 2) New Features (With Technical Detail)

### App-mode onboarding on `app.elizacloud.ai`
- **Feature:** App-mode entry routes now land authenticated users directly in their dedicated agent experience on the `app.*` hosts: **#17752**  
  https://github.com/elizaos/eliza/pull/17752

**Why it matters:** previously `app.elizacloud.ai` was effectively a second hostname for the marketing build. This introduces host-mode branching and a dedicated “entry route” that resolves/provisions and resumes the user’s agent session.

**Implementation notes (developer-facing):**

- UI logic is implemented in `packages/ui/src/cloud/app-mode/*`.

## 7) Breaking Changes / Migration Warnings (V1 → V2 and runtime contracts)

### (A) Planner tool-call schema: `eliza_turn_scope` is now required
PR **#18247** makes the “turn scope” explicit and mandatory for planner tool calls. Any custom tool runner / planner delegate emitting tool calls must include `eliza_turn_scope`.

**Migration sketch (conceptual):**
```ts
// When emitting a tool call from your planner delegate:
return {
  tool: "YOUR_TOOL",
  args: {
    /* your args */
    eliza_turn_scope: "more_work_pending" // or "turn_complete"
  }
};
```
If you omit it, expect evaluator/termination behavior to regress (e.g., early termination or double-send patterns).

### (B) Cloud A2A system-policy injection is no longer allowed
PR **#17643** rejects caller-authored `system` messages. If you used A2A as a way to push system prompts at runtime, you must:
- move policy into the agent’s configured system prompt / server-side policy store, or
- implement a server-owned control surface that mutates policy with explicit authorization (do **not** tunnel via A2A).

### (C) Environment/tooling pins that can break local builds
- Repo-wide Bun pin alignment (not new this week but actively enforced) is centered on **Bun `1.3.14`** (see unification work referenced in weekly summary and PRs like **#17044**, **#17653**). If your local environment floats Bun versions, expect CI parity issues.

### (D) V1 → V2 operational migration notes (Cloud backups/snapshots)
- The Cloud work includes explicit guardrails around legacy snapshot retention budgets (e.g., **#17180** “bound v1 snapshot retain budget by what restore can consume”). While not a “one-click migration,” it’s a warning that v1-era assumptions about unlimited snapshot retention or restore consumption no longer hold.

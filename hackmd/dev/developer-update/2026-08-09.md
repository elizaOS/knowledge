# ElizaOS Developer Update — Week of 2026-08-03 to 2026-08-09

This week concentrated on production stability (Cloud inference + voice), security hardening at public boundaries (A2A + webhooks), and developer-experience improvements (CI reliability, deterministic tests, and contribution tooling). Discord discussions also confirmed the project’s continued focus on open-source agent software, fully decoupled from token economics (non-technical context, but it impacts docs and repo messaging).

## 1) Core Framework (Runtime, Architecture, Plugin System)

### Runtime ownership + lifecycle hardening
Several merges tightened “ownership” semantics so long-running or background work is abortable, attributable, and doesn’t leak state:

- **Owner-controlled benchmark/boot + safer shutdown paths** — improves runtime determinism and prevents “losing” tasks from continuing after timeouts ([#17531](https://github.com/elizaos/eliza/pull/17531)).
- **Provider deadlines made cancellation-safe** — avoids caching “timeout as empty context” and prevents provider work from running after a deadline ([#17490](https://github.com/elizaos/eliza/pull/17490)).
- **Tool failures now answer honestly (instead of generic fallback)** — planner responds with actionable error context when tool calls fail ([#17501](https://github.com/elizaos/eliza/pull/17501)).

### Security envelope hygiene in the core message path
A critical fix prevented the “untrusted external-content envelope” from being echoed back into chat or used as action inputs by downstream features/actions ([#17629](https://github.com/elizaos/eliza/pull/17629)). This reduces prompt contamination and avoids subtle regressions where actions use `message.content.text` as a query/name/target.

### Cloud ↔ Runtime voice parity + canonical persistence
Voice reliability improvements focused on the canonical Durable Object / shared-runtime paths (not legacy bridges):

- **Persist interrupted turns on the canonical voice path** (fixing a previously patched-but-unused legacy route) ([#17644](https://github.com/elizaos/eliza/pull/17644)).
- **Warm every cold cache a realtime voice turn reads** to reduce first-turn latency and reduce warm-up failures in staging/production voice sessions ([#17744](https://github.com/elizaos/eliza/pull/17744)).
- **Align private voice (VOICE_DM) response grammar with direct responses** to prevent unexpected “shouldRespond” gating in 1:1 voice contexts ([#17863](https://github.com/elizaos/eliza/pull/17863)).

## 2) New Features (With Technical Detail + Examples)

### Fish Audio streaming TTS (low-latency voice output)
A new streaming TTS integration landed for voice sessions, designed for real-time conversational flow ([#17709](https://github.com/elizaos/eliza/pull/17709)). This adds a dedicated plugin package and cloud wiring to stream audio frames rather than waiting for a full synthesis blob.

**What you get**
- Streaming audio over the voice session pipeline (faster “time-to-first-audio”).
- A plugin surface (`plugins/plugin-fish-audio`) suitable for runtime selection.

**Example: enable the plugin in a character/runtime config**
```ts
// character.config.ts (conceptual; exact wiring depends on your runtime bootstrap)
export const character = {
  name: "Eliza",
  plugins: [
    "@elizaos/plugin-fish-audio",
  ],
  secrets: {
    FISH_AUDIO_API_KEY: process.env.FISH_AUDIO_API_KEY!,
  },
};
```

## 3) Bug Fixes (Critical Issues + Root Cause Context)

### Production inference alternation: “billing authorization is warming up”
A high-severity production issue caused an observed ~50% failure rate due to authorization cache warm-up behavior alternating success/failure. The fix republishes the org-balance gate hint after a debit so subsequent turns don’t trip warming again ([#17745](https://github.com/elizaos/eliza/pull/17745)). This was shipped to production in the **develop → main promotion** ([#17865](https://github.com/elizaos/eliza/pull/17865)).

**Why it mattered**
- The model path was healthy; the failure was upstream gating/caching.
- Symptoms manifested as stable inference latency but intermittent 503s.

---

### A2A trust boundary hardening: reject caller-authored system policy
Public per-agent A2A endpoints now reject caller-supplied `system` messages *before* billing reservation/provider dispatch ([#17643](https://github.com/elizaos/eliza/pull/17643)). This closes a class of “system prompt injection at API boundary” vulnerabilities.

**Impact**
- Existing clients that were sending `system` role messages to A2A must migrate to supported patterns (see **Breaking Changes**).

---

### Google Calendar webhook ingress hardened (security + exactly-once receipts)
The calendar plugin’s webhook ingress path was hardened as a single security boundary: route registration is now configuration-gated; requests require a destination-bound HMAC capability; authorization happens before any DB writes; and valid notifications produce immutable receipts with exactly-once enqueue semantics ([#17649](https://github.com/elizaos/eliza/pull/17649), pending merge at time of aggregation).

**Why this is critical**
- Prevents public route exposure by default.
- Prevents stateless probes from resolving services or touching the DB.

---

### Planner/tooling reliability: required tool calls vs reasoning token burn
Reasoning-capable models can exhaust completion tokens before emitting the required tool call when `toolChoice: required` and completion budgets are tight. The planner loop now avoids starving tool calls and widens stream-start retry logic ([#17630](https://github.com/elizaos/eliza/pull/17630)).

---

### Discord readiness race on ingress
Discord can emit `messageCreate` immediately after `ClientReady` while async readiness hydration is still running. The plugin now blocks ingress until identity is fully ready ([#17645](https://github.com/elizaos/eliza/pull/17645)).

## 4) API Changes (Developer-Facing)

### Cloud internal route mount changes: account-pool broker under `/api/internal`
An internal HTTP surface was previously unreachable in production due to prefix mismatch. Routes are now mounted under `/api/internal` so the dispatcher can reach them ([#17782](https://github.com/elizaos/eliza/pull/17782)).

**If you maintain internal callers**
- Update any hardcoded paths expecting `/internal/...` to `/api/internal/...` (exact route remains defined in `account-pool-broker-routes.ts`).

---

### Cross-origin SSO bridge (dashboard ↔ app host)
A cross-origin SSO bridge was added to support “one login across the dashboard and app origins”, using atomic single-use codes stored in Postgres and fail-closed logout handling ([#17788](https://github.com/elizaos/eliza/pull/17788)). This was included in the production promotion ([#17865](https://github.com/elizaos/eliza/pull/17865)).

**UI surfaces**

### A2A input validation: `system` messages disallowed
As above, A2A now rejects caller-authored system role messages ([#17643](https://github.com/elizaos/eliza/pull/17643)). Treat this as an API contract change at the public boundary.

## 6) Model Provider Updates (OpenAI/Anthropic/DeepSeek/etc.)

### OpenAI plugin: streaming + retry behavior
Planner/proxy behavior adjustments touched provider streaming start retry logic and required tool-call handling ([#17630](https://github.com/elizaos/eliza/pull/17630)).

### Prompt cache reuse improvements (Cerebras + prefix-block caching)
Stage-1 prompt structure was reordered to maximize prefix cache hits by moving volatile fields (e.g., `CURRENT_TIME`) to avoid invalidating large cached blocks ([#17515](https://github.com/elizaos/eliza/pull/17515)). This reduces latency/cost for providers with strong prefix caching.

### SDK dependency updates (OpenAI-compatible)
The repo bumped `@ai-sdk/openai-compatible` from `2.x` to `3.x` ([#17760](https://github.com/elizaos/eliza/pull/17760)). If you maintain downstream provider adapters, revalidate any code that depended on older Vercel AI SDK behaviors/types.

## 7) Breaking Changes / Migration Warnings (V1 → V2 and Operational Contracts)

### V1 snapshot retain budget is now bounded by restore capacity
Cloud backup safety alignment bounds the v1 snapshot retention budget to what restore can consume ([#17180](https://github.com/elizaos/eliza/pull/17180)). This is explicitly “v1 safety alignment” and does **not** implement the larger v2 additive protocol/rollout (tracked in [#17172](https://github.com/elizaos/eliza/issues/17172), referenced by the PR body).

**Migration note**
- If you relied on keeping many v1 snapshots “just in case”, expect aggressive pruning aligned to restore realities. Plan a v2 backup protocol adoption when available.

---

### A2A boundary: sending `system` messages is no longer permitted
If your integration used A2A to inject system policy per request, it will now be rejected ([#17643](https://github.com/elizaos/eliza/pull/17643)). Move system policy into server-controlled configuration (character config / agent runtime settings) rather than client-supplied chat input.

---

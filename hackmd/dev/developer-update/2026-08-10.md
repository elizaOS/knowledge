## 2) New Features

### App-mode onboarding on `app.elizacloud.ai`
**[#17752](https://github.com/elizaos/eliza/pull/17752)** introduces **app-mode**: when users log in on the app host, they are routed directly into *their dedicated agent* (auto entry/chooser/resume/fallback), instead of seeing the marketing surface.

**Developer implications**
- Hostname now matters: the UI can branch behavior based on app vs apex host.
- A guard ensures the expected host-mode is enforced (and tested) so deploys don’t silently drift.

### Cross-origin SSO Bridge (Dashboard ↔ App)
**[#17788](https://github.com/elizaos/eliza/pull/17788)** adds an SSO bridge that supports “login once” across `app.elizacloud.ai` and other Cloud surfaces, using **atomic single-use codes stored in Postgres**, PKCE binding, and “fail-closed logout” semantics.

Minimal integration sketch (browser-side):
```ts
// Pseudocode: initiate SSO bridge from dashboard → app host
const res = await fetch("/auth/sso-bridge", { method: "POST", credentials: "include" });
const { code } = await res.json();

location.href = `https://app.elizacloud.ai/sso-bridge?code=${encodeURIComponent(code)}`;
```

### Fish Audio streaming TTS (voice)
**[#17709](https://github.com/elizaos/eliza/pull/17709)** integrates **Fish Audio streaming TTS** into the Cloud voice session pipeline, enabling lower-latency, more natural realtime voice turns.

Operational follow-up that materially improves cold-start voice reliability:
- **Warm every cold cache a realtime turn reads**: **[#17744](https://github.com/elizaos/eliza/pull/17744)**.
- **Persist interrupted voice turns on the canonical Durable Object path**: **[#17644](https://github.com/elizaos/eliza/pull/17644)**.

### Gmail as a MESSAGE send connector (Google Workspace)
Two PRs combine into a meaningful new capability:
- **Wire Gmail as a MESSAGE send connector; re-enable “new email” send**: **[#18112](https://github.com/elizaos/eliza/pull/18112)**  
- **Smart channel routing for `MESSAGE op=send`** (room participant resolution before rolodex; subject param support; email literal targets): **[#18111](https://github.com/elizaos/eliza/pull/18111)**

Example: sending email through the MESSAGE action (conceptual)
```ts
await runtime.actions.MESSAGE({
  op: "send",
  // Supports email-literal targets after #18111
  to: ["alice@example.com"],
  subject: "Follow-up",
  text: "Thanks for the meeting—here are the notes..."
});
```

### UI: per-connector Settings detail pages (Delegate/Bot lens)
**[#18175](https://github.com/elizaos/eliza/pull/18175)** migrates Settings → Connectors into per-connector detail pages, improving discoverability and reducing misconfiguration (especially for multi-surface connector deployments).

## 3) Bug Fixes (critical + with context)

### Billing auth alternation (50% inference failures) fixed in production
The release promotion **[#17865](https://github.com/elizaos/eliza/pull/17865)** shipped the fix for an issue where production inference alternated success/failure with “Billing authorization is warming up”. The underlying patch was **[#17745](https://github.com/elizaos/eliza/pull/17745)**: republish org-balance gate hints after a debit to avoid oscillation.

### Tool-call starvation on reasoning models (planner budget)
**[#17630](https://github.com/elizaos/eliza/pull/17630)** fixes a failure mode where reasoning models consume the entire completion budget *before emitting* a required tool call. The runtime now widens retries / budgets so `toolChoice: required` doesn’t dead-end mid-reasoning.

### “External-content security envelope” leaking into downstream actions/tools
**[#17629](https://github.com/elizaos/eliza/pull/17629)** prevents a structural bug where hardened incoming messages were wrapped in-place, and later code that treated `message.content.text` as a plain query/name accidentally carried the entire envelope (markers + payload). This impacted search, skill ops, documents, and app-control surfaces.

### Telegram onboarding continuation secured (browser handoff)
**[#18101](https://github.com/elizaos/eliza/pull/18101)** addresses a real security gap: browser authentication alone must not bind a Telegram identity. The fix carries a bot-issued opaque continuation through auth and validates Telegram HMAC/freshness server-side before linking.

Related open bug report (still relevant for integrators):  
- **Telegram system-bot onboarding dead / identity not durably bound**: **[#17888](https://github.com/elizaos/eliza/issues/17888)** (open)

### OAuth success page no longer trusts query params
**[#18065](https://github.com/elizaos/eliza/pull/18065)** requires verified OAuth markers on `/auth/success` so anonymous navigation cannot render a “Connected” state from query parameters.

### Discord readiness race: message ingress before identity hydration
**[#17645](https://github.com/elizaos/eliza/pull/17645)** ensures Discord connector waits for “ready identity” before ingesting `messageCreate`, preventing mis-attributed or partial state during startup.

### Reliability of agent memory/recall after latency regression
- **Maximize prompt cache reuse (Cerebras)**: **[#17515](https://github.com/elizaos/eliza/pull/17515)** reorders prompt composition to improve prefix cache hit rates.
- **Relationships graph builder stale-serve + rolodex bounds**: **[#17876](https://github.com/elizaos/eliza/pull/17876)** reduces worst-case recall turns (previously measured 33–56s).

## 4) API Changes (developer-facing)

### A2A chat boundary: `system` messages are rejected
As of **[#17643](https://github.com/elizaos/eliza/pull/17643)**, public per-agent A2A endpoints reject caller-authored `system` messages. If you previously injected system directives through A2A, you must migrate to:
- tool calls,
- user/assistant messages, or
- server-attested policy configuration (not caller-authored runtime messages).

### OAuth success proof verification route introduced
**[#18065](https://github.com/elizaos/eliza/pull/18065)** adds server verification to support `/auth/success` rendering. If you maintain custom OAuth providers, ensure you’re completing the proof step (see updated Cloud worker routes in that PR).

### Managed agent marker consistency
**[#18165](https://github.com/elizaos/eliza/pull/18165)**: Cloud-managed agents are always marked `ELIZA_CLOUD_PROVISIONED`. If your tooling checks this env var to branch behavior (e.g., diagnostics vs managed runtime), this should now be reliable.

## 7) Breaking Changes / V1 → V2 Migration Warnings

### Breaking: A2A no longer accepts caller `system` messages
If you have V1-era integrations that push system policy via message history, you must migrate. Post-change, **A2A treats system policy as a server-controlled boundary**, not caller-supplied content. See **[#17643](https://github.com/elizaos/eliza/pull/17643)**.

### Potentially breaking: Host-mode routing (apex vs app host)
With **app-mode** (**[#17752](https://github.com/elizaos/eliza/pull/17752)**), deployments that assume identical behavior across `eliza.app` / `app.elizacloud.ai` may see different routing. If you embed the Cloud UI or run reverse proxies, ensure Host headers are preserved and that your custom domains map intentionally.

### Runtime/CI environment pin: Bun `1.3.14`
The repository is converging on Bun `1.3.14` pins (see **[#17044](https://github.com/elizaos/eliza/pull/17044)** and **[#17653](https://github.com/elizaos/eliza/pull/17653)**). If your plugin CI or local dev depends on Bun canary behaviors, expect drift and update accordingly.

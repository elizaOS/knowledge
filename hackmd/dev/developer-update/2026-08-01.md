## 2) New Features

### Solana pre-transaction verification: `@pnllabs/plugin-pnllabs` (community plugin release)
PnL Labs released a new Solana-focused plugin intended to provide **pre-transaction verification** before an agent signs/sends a transaction. Key capabilities:

- **Wallet trust scoring** based on realized on-chain PnL (intended to reduce blindly following “smart money” lists)
- **Token safety checks**
- **Real trade cost analysis**
- **Funding forensics**

Discord context: PnL Labs reported auditing 30 tracked “smart money” wallets and found ~half were actually losing money—motivating a verification-first approach before copying trades.

**Install**
```bash
npm install @pnllabs/plugin-pnllabs
```

**Usage (example)**
Exact wiring depends on your ElizaOS runtime setup, but the intended flow is:

1) register plugin
2) call verification checks prior to transaction construction/signing
3) block or require additional confirmation on low-trust or unsafe results

```ts
// Pseudocode example showing the intended integration pattern.
// Adjust to your agent runtime's plugin registration + action/tool invocation APIs.

import { PnLLabsPlugin } from "@pnllabs/plugin-pnllabs";

export const agentConfig = {
  plugins: [
    PnLLabsPlugin({
      // Free tier: no API key required (per release notes)
      // Paid usage: pay-per-call via x402 after free tier
    }),
  ],
};

// Before executing a Solana trade:
async function guardedSwap({ wallet, tokenMint, quote }) {
  const trust = await agent.tools.pnllabs.walletTrust({ wallet });
  const tokenSafety = await agent.tools.pnllabs.tokenSafety({ mint: tokenMint });
  const costs = await agent.tools.pnllabs.tradeCosts({ quote });

  if (trust.score < 0.6 || tokenSafety.risk === "high") {
    throw new Error(
      `Blocked trade: trust=${trust.score}, risk=${tokenSafety.risk}`
    );
  }

  return agent.tools.solana.executeSwap({ quote, costs });
}
```

## 3) Bug Fixes (critical)

### Agent deletion failures due to state mismatches
**Impact:** agents could become undeletable or partially deleted, leaving orphaned records/resources and causing follow-on errors in provisioning and monitoring.

**Fix:** lifecycle operations now handle mismatch conditions correctly and avoid failing mid-flight.  
PRs: [#17260](https://github.com/elizaos/eliza/pull/17260), [#17251](https://github.com/elizaos/eliza/pull/17251)

### Incorrect monitoring/error flagging on legitimate work
**Impact:** background tasks could be misclassified as errors, leading to noisy alerts and potentially automated remediation (restarts/pauses) triggering unnecessarily.

**Fix:** refined startup + monitoring logic to reduce false positives.  
PR: [#17292](https://github.com/elizaos/eliza/pull/17292)

### Managed canary staleness + test coverage regressions
**Impact:** stale canaries could cause recurring pipeline failures and reduce confidence in lifecycle correctness.

**Fix:** restored lifecycle test coverage + implemented safe recovery for stale managed canaries.  
PRs: [#17173](https://github.com/elizaos/eliza/pull/17173), [#17169](https://github.com/elizaos/eliza/pull/17169)

### Snapshot retention edge cases
**Impact:** incorrect retention logic can either leak storage (retaining too much) or risk data loss (retaining too little).

**Fix:** snapshot retention logic corrected and covered across multiple files.  
PR: [#17180](https://github.com/elizaos/eliza/pull/17180)

## 4) API Changes

No explicitly documented public API signature changes were identified in this week’s aggregated notes. However, there are **behavioral changes** developers should account for:

- **Lifecycle operations are stricter and more consistent** after the deletion/mismatch fixes ([#17260](https://github.com/elizaos/eliza/pull/17260), [#17251](https://github.com/elizaos/eliza/pull/17251)). If you had downstream tooling that relied on partial deletion or silent failures, update it to handle explicit failures and/or new consistency checks.
- **Monitoring/task classification behavior changed** ([#17292](https://github.com/elizaos/eliza/pull/17292)). If you parse logs/metrics to detect failures, re-baseline alerts after upgrading.

If you maintain custom plugins that hook into lifecycle or monitoring events, validate them against these PRs before rolling to production.

## 7) Breaking Changes (V1 → V2 migration warnings)

No new V1→V2 breaking changes were explicitly called out in this week’s summaries.

That said, **agent lifecycle and monitoring behavior** changed meaningfully (see PRs above). Treat upgrades as potentially breaking if you:
- depend on legacy deletion semantics,
- assume specific monitoring error classifications,
- or have custom infrastructure around managed canaries/snapshots.

Also note: community discussion indicates **ElizaOS v3 is available in the main repo** (clone/build from GitHub). If you are migrating across major versions (V1/V2/V3), validate:
- plugin registration/loading order,
- lifecycle hooks,
- and monitoring/telemetry expectations
in a staging environment first.

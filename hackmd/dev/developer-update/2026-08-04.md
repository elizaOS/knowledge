# ElizaOS Developer Update (2026-07-28 → 2026-08-03)

This update summarizes key engineering changes across the ElizaOS monorepo and highlights developer-facing workflow changes and runtime reliability improvements, plus notable community onboarding friction reported in Discord.

---

## 1) Core Framework (Architecture / Plugin System / Agent Runtime)

### Owner-controlled boot + benchmark lifecycles
Agent boot and benchmarking were hardened to ensure **runtime/database shutdown is owned and deterministic**, and that long-running work is not left running after timeouts. This reduces “zombie” provider calls, leaked handles, and inconsistent agent state during CLI workflows.

- PR: **fix(agent): make benchmark and boot work owner-controlled** ([#17531](https://github.com/elizaOS/eliza/pull/17531))

Key effects:
- Eliminates unsafe `Promise.race` patterns that timed out without aborting the losing execution path.
- Tightens boot telemetry and deferred boot ownership semantics.
- Improves plugin registration stop behavior (prevents late plugin registration after shutdown).

### Provider deadline handling made cancellation-safe (core runtime)
A critical correctness fix ensures provider deadlines do not poison subsequent turns by caching timeout artifacts as empty context, and that timeouts are handled with cancellation semantics rather than “race-and-forget”.

- PR: **fix(core): make provider deadlines cancellation-safe** ([#17490](https://github.com/elizaOS/eliza/pull/17490))

If you maintain custom providers, audit any internal timeout logic to ensure it respects abort signals and does not persist partial/empty results.

### Snapshot/backup safety guardrails (Cloud + agent API boundary)
Cloud snapshot retention is now bounded by what restore can consume (v1 safety alignment). This is part of ongoing backup protocol stabilization; note that the broader v2 backup protocol work remains out of scope for this slice.

- PR: **fix(cloud): bound the v1 snapshot retain budget by what restore can consume** ([#17180](https://github.com/elizaOS/eliza/pull/17180))

## 3) Bug Fixes (critical fixes with technical context)

### Stage-1 time correctness: `CURRENT_TIME` now always renders
A production-class incident was traced to an intent-gate that sometimes prevented time injection even when the system prompt promised time correctness. The fix removes the fragile prose-regex gate so Stage-1 always renders `CURRENT_TIME`.

- PR: **fix(core): Stage-1 always renders CURRENT_TIME — delete the prose-regex intent gate** ([#17500](https://github.com/elizaOS/eliza/pull/17500))

Impact:
- Prevents wrong-date/wrong-weekday responses caused by stale prompt time context.
- Improves determinism for downstream tools and planners that depend on accurate timestamps.

### Tool failures now answer honestly (instead of generic planner fallback)
Several real incidents showed failed tools being translated into a generic “runtime step failed” apology, even when the system could produce a meaningful partial answer or a precise failure explanation. The fix ensures tool failure is surfaced at the correct boundary.

- PR: **fix: tool failures answer honestly instead of feeding the generic fallback** ([#17501](https://github.com/elizaOS/eliza/pull/17501))

If you implement tool plugins, ensure your action handlers return structured failures compatible with the runtime’s error policy (rather than throwing opaque errors).

### CI stability: protect GitHub runner control directories from pruning
Self-hosted runners failed intermittently because workspace pruning deleted runner-owned directories (e.g. `_temp`) while workflows were still running.

- Issue: **fix(ci): protect runner control directories from workspace pruning** ([#17534](https://github.com/elizaOS/eliza/issues/17534))
- PR: **fix(ci): protect runner control directories from pruning** ([#17535](https://github.com/elizaOS/eliza/pull/17535))

Outcome:
- Pruner now excludes runner-owned control directories (`_temp`, `_actions`, `_tool`, `_update`, `_PipelineMapping`).
- Regression tests ensure protection cannot be removed without failing CI.

### Develop PR gate now runs plugin unit tests when plugin packages change
A real defect landed because plugin unit tests only ran post-merge. The develop PR gate now runs **changed-plugin-scoped unit tests** pre-merge.

- Issue: **[agent] fix(ci): run plugin unit tests on the develop PR gate** ([#17550](https://github.com/elizaOS/eliza/issues/17550))
- PR: **ci(develop-pr): gate changed plugin packages with their own unit tests** ([#17552](https://github.com/elizaOS/eliza/pull/17552))

Developer impact:
- PRs touching `plugins/**` may now fail earlier with plugin test failures that previously surfaced only after merge.
- Expect additional CI wall time proportional to the number of changed plugin packages.

## 4) API Changes (developer-visible modifications)

### Cloud Mobile PKCE auth lifecycle (server-side; disabled-by-default)
A major Cloud server capability adds an Authorization Code + PKCE lifecycle for a fixed mobile client and callback route. This change is explicitly **flag-guarded** and fails closed unless enabled in `staging`/`production`.

- PR (open): **feat(cloud): add disabled mobile PKCE auth lifecycle** ([#16641](https://github.com/elizaOS/eliza/pull/16641))

Key API behaviors (high level):
- New mobile auth exchange + acknowledgement lifecycle.
- Header-only credential transport enforced; query-string tokens rejected for mobile credentials.
- Additive DB migrations; does not change existing browser/desktop auth contracts.

If you maintain Cloud API consumers:
- No behavior changes unless the feature flag(s) are enabled.
- Watch this PR for generated SDK wrapper updates and new error codes (e.g. transport-forbidden semantics).

## 6) Model Provider Updates (OpenAI, Anthropic, Cerebras, local, etc.)

A performance-oriented change reorders volatile prompt elements (notably `CURRENT_TIME`) to maximize prefix cache reuse for providers that cache fixed prefix blocks.

## 7) Breaking Changes / Migration Warnings (V1 → V2, workflow gates)

### Breaking: Evidence + attribution enforcement is now “workflow-default”
The `eliza.army` launch ([#17424](https://github.com/elizaOS/eliza/pull/17424)) tightened repo-wide expectations around:
- evidence completeness (screenshots/logs/trajectories where applicable)
- model/provider attribution formats
- policy-driven CI checks (PR templates + validators)

If you contribute frequently, expect:
- PRs to be blocked by evidence gates if you mark required rows as `N/A` for UI-touching diffs.
- Attribution checks to reject incomplete provider/model identifiers.

### Breaking (CI): develop PR gate behavior changed for plugins
With [#17552](https://github.com/elizaOS/eliza/pull/17552), plugin changes now run pre-merge unit tests. If your workflow depended on “merge first, fix after,” that path will now be blocked.

### V1 → V2 migration note (Cloud backups)
The snapshot retain budget fix ([#17180](https://github.com/elizaOS/eliza/pull/17180)) is explicitly v1 safety alignment. The larger v2 backup/restore protocol is still evolving; treat any backup-interop assumptions as unstable unless documented in the Cloud backup design notes referenced in the linked issue thread.

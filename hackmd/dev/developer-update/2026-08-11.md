# ElizaOS Developer Update (2026-08-04 → 2026-08-10)

This update summarizes core runtime, Cloud, and plugin work landing (or actively staged) during the week leading up to **2026-08-11**, with emphasis on changes that affect developers building agents and integrations on ElizaOS.

**Primary repos:** [`elizaos/eliza`](https://github.com/elizaos/eliza)

## 1) Core Framework

### Runtime determinism, delivery semantics, and planner hygiene
A large cluster of changes tightened the “one turn → one coherent user-facing reply” contract across channels, especially where tools/sub-agents are involved:

- **Preserve tool outputs when the planner dies mid-turn** and treat certain provider 400s as transient: [#18180](https://github.com/elizaOS/eliza/pull/18180)  
  *Why it matters:* if your plugin returns a `verifiedUserFacing` tool result, the runtime now strongly prefers delivering that preserved result rather than falling back to generic apologies.

- **Turn delivery floor + observability** (ensure a finished turn delivers something, and record deliberate silence as terminal): [#17631](https://github.com/elizaOS/eliza/pull/17631)

- **“AddressedTo” engagement gate** expanded beyond tool-promotion into full routing (reduces unprompted replies in group channels):  
  - framework plumbing: [#18174](https://github.com/elizaOS/eliza/pull/18174)  
  - group-channel suppression coverage: [#18183](https://github.com/elizaOS/eliza/pull/18183)

- **Planner tool-call scope is now required** to avoid premature turn termination: [#18247](https://github.com/elizaOS/eliza/pull/18247)  
  This is effectively a contract change for planner/tool authors (details in **Breaking Changes**).

### Provider budgeting and cancellation correctness
- Provider deadlines are now **cancellation-safe** (avoid “timeout cached as empty context” pathologies): [#17490](https://github.com/elizaOS/eliza/pull/17490)  
- Follow-on latency repair for memory/relationships turns by **stale-serving the relationships graph** and bounding rolodex provider work: [#17876](https://github.com/elizaOS/eliza/pull/17876)

### Security envelope hardening (core)
- External-content “security envelope” is no longer echoed into action inputs/queries (prevents tool-side leakage of envelope markers and avoids confusing downstream parsers): [#17629](https://github.com/elizaOS/eliza/pull/17629)

### Operational standardization
- Repo-wide runtime alignment continued: Bun pins and CI invariants (notably Bun `1.3.14`) were reinforced in multiple lanes and contracts (e.g. [#17653](https://github.com/elizaOS/eliza/pull/17653), and the cross-repo milestone tracked under [#17044](https://github.com/elizaOS/eliza/pull/17044)).

- Change: [#18247](https://github.com/elizaOS/eliza/pull/18247)

**Example (tool call args):**
```json
{
  "tool": "TASKS_MANAGE_ISSUES",
```

## 7) Breaking Changes / Migration Warnings (V1 → V2, behavior shifts)

### Required: `eliza_turn_scope` on planner tool calls
As noted above, [#18247](https://github.com/elizaOS/eliza/pull/18247) hardens a previously-optional field into a required contract in practice. If you have:
- custom planners,
- tool routers,
- or external orchestration that fabricates tool-call JSON,

…you should update your payload generation to always include an explicit turn scope.

### Group-channel reply behavior changed (addressedTo gate)
The broader addressedTo routing gate work ([#18174](https://github.com/elizaOS/eliza/pull/18174), [#18183](https://github.com/elizaOS/eliza/pull/18183)) can change whether your agent responds in group channels when not explicitly addressed. If you relied on “ambient” replies for monitoring/broadcast scenarios, you may need to:
- mark messages as addressed (mention/reply), or
- switch to a DM/API channel, or
- adjust your connector’s addressing signals.

### Cloud backup/snapshot safety alignment (V1 surface)
If you are still operating legacy v1 snapshot/restore pathways, note the safety alignment that bounds retain budget by what restore can consume:
- [#17180](https://github.com/elizaOS/eliza/pull/17180)

This is intentionally scoped to immediate safety; it does not implement the full v2 backup protocol described in the linked issue lineage (see PR body for scope notes).

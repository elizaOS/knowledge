## Patterns / Themes indicating deeper architectural problems
- **“Green but not proving what we think it proves”**: CI lanes that pass while exercising the wrong environment (staging vs prod) indicate a need for stronger **environment attestation** and fail-closed assertions.
- **Onboarding as a multi-surface, multi-identity pipeline**: Telegram flow failures show that onboarding spans bot → web → auth → identity-link → agent routing; without a single end-to-end owned contract, regressions emerge in the seams.
- **Operational regressions tied to config/constants**: hard-coded autoscaler limits and default production URLs suggest configuration drift risk; critical paths should be explicitly parameterized and validated at boot.
- **Cold-start/caching behavior as user-visible UX blockers**: auth provider enumeration latency and cache-warming classes show that edge/runtime cold paths must be treated as first-class performance work, not incidental.

---

## Process improvement recommendations
1. **Environment attestation everywhere:** require tests/jobs to assert `(baseUrl, host, envName, credential scope)` explicitly; fail if defaults are used.
2. **End-to-end “first success” contracts:** maintain a small suite of connector onboarding E2Es (Telegram/Discord/Webhook) that verify durable identity linking and second-message routing.
3. **Operational SLO dashboards tied to deploys:** track provisioning failure rate, time-to-failure-notification, and login time-to-interactive with annotations per deploy SHA.
4. **Config lint + boot-time guards:** detect hard-coded ceilings / production defaults in staging contexts; enforce “no prod default” in non-prod builds unless explicitly whitelisted.
5. **Faster user-visible failure:** reduce watchdog timeouts and add intermediate status updates so users aren’t stalled for ~52 minutes without actionable feedback.

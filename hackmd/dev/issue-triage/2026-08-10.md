## Patterns / Themes Suggesting Deeper Architectural Issues
- **Environment drift + false confidence from “green” CI:** staging/prod targeting ambiguity (e.g., defaulting to production) indicates missing fail-closed environment contracts and insufficient environment-specific secrets hygiene.
- **Onboarding is a multi-surface system with weak end-to-end guarantees:** connector onboarding (Telegram) depends on correct host routing, caching correctness, and secure identity proof; small misconfigs create total funnel failure.
- **Operational limits encoded as constants instead of config:** autoscaler `maxNodes` hardcoding and capacity ceiling mismatches imply insufficient configuration validation and runtime contract tests.
- **Cold-start and upstream dependency latency on critical entrypoints:** `/steward/auth/providers` gating all login actions suggests missing caching/edge strategies on “first paint” endpoints.

---

## Process Improvement Recommendations
1. **Fail-closed environment contracts in CI and runtime**
   - Require explicit base URLs for staging/prod lanes and **assert resolved hostnames** in tests.
   - Add a “no-default-to-prod” guard for any job labeled staging/QA.
2. **Release/deploy alignment checks**
   - Add a lightweight check ensuring **production daemons are not pinned behind** required fixes (a “commit parity” or “minimum version” gate).
3. **Onboarding E2E certification for connectors**
   - Maintain a small set of **redacted, real-credential E2E** tests (Telegram/Discord/web) that prove identity binding + second-message routing.
4. **SLOs + alerting for funnel-critical endpoints**
   - Establish p95 targets and alerts for provisioning success rate, provisioning time-to-failure notification, and login provider list latency.
5. **Canonical comms + anti-scam posture**
   - Publish and pin official links, distribution status, and token posture; add automated moderation rules to reduce impersonation/scam attempts.

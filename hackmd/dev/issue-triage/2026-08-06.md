# Patterns / Themes Suggesting Deeper Architectural Problems
- **Trust & safety is now a core operational dependency:** Discord is functioning as support + product comms + onboarding. Without hardened moderation and official support paths, security incidents become inevitable.
- **Contributor experience hinges on CI determinism:** Multiple items point to CI/graph ordering and workflow semantics as a major throughput limiter (nondeterminism + fork approval behavior).
- **Blurry boundary between OSS elizaOS and token/commercial narrative:** The absence of a stable “what we are shipping” contract is amplifying conflict, reducing contributor confidence, and creating ongoing brand risk.

# Process Improvement Recommendations
1. **Establish a standing “Security & Trust” rotation** (even lightweight): daily checks of Discord spam/scam logs, pinned warnings, and rapid ban/escalation procedures.
2. **Publish and maintain a canonical “Project Status & Scope” document** with explicit boundaries (OSS runtime vs any token/commercial activities).
3. **Add CI reliability SLOs + ownership:** track flaky workflow rates; require a regression test/contract for each CI incident (Turbo ordering, check polling, etc.).
4. **Improve onboarding funnel resilience:** a single “Start Here” link, Discord pins, and a documented public support intake that reduces DM-based scams.
5. **Crisis communications protocol:** pre-agreed template for announcements (what happened, what changes, what users should do next, where to get updates), posted to GitHub + Discord simultaneously.

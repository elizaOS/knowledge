# ElizaOS Weekly Newsletter (2026-07-27 → 2026-08-02)

## 1) Executive Summary

**1. eliza.army officially landed (skill + leaderboard).**  
The biggest milestone this week was the merge of **“launch eliza.army contribution skill and leaderboard”** into `develop` ([elizaos/eliza#17424](https://github.com/elizaos/eliza/pull/17424)). This introduces a *packaged contribution skill* (for issue-finishing/PR-review workflows) plus a *public Vite site* that explains the process and surfaces a GitHub-backed leaderboard. It’s also a meaningful step toward more structured, transparent, and rewardable community contributions.

**2. CI reliability improved in ways that directly help contributors.**  
Several changes focused on making CI failures more actionable and less flaky—especially for plugin work and self-hosted runners. Highlights include gating changed plugins with their own unit tests before merge ([#17552](https://github.com/elizaos/eliza/pull/17552)) and protecting GitHub Actions runner control directories from over-aggressive workspace pruning ([#17535](https://github.com/elizaos/eliza/pull/17535)).

**3. Agent/runtime correctness: fewer “mystery failures,” more honest behavior.**  
Core fixes this week focused on ensuring the system behaves predictably under failure and time pressure—e.g., provider deadlines becoming cancellation-safe ([#17490](https://github.com/elizaos/eliza/pull/17490)) and tool failures returning *truthful, specific errors* instead of falling back to generic apologies ([#17501](https://github.com/elizaos/eliza/pull/17501)).

## 2) Development Updates

### New Features & Platform Additions
- **eliza.army contribution skill + leaderboard** ([#17424](https://github.com/elizaos/eliza/pull/17424))  
  Adds a bundled “contribute-to-eliza” skill that emphasizes claims, evidence, validation, and explicit model attribution. Also ships the `packages/eliza-computer` site that explains workflow, lists open work, and renders leaderboard snapshots.

### CI/CD & Infrastructure Hardening
- **Pre-merge plugin test gating for `develop` PRs** ([#17552](https://github.com/elizaos/eliza/pull/17552))  
  A practical improvement: if you change a plugin package that has unit tests, CI now runs those tests in the develop PR gate—reducing the chance of “it broke right after merge.”
- **Runner workspace pruning made safe**  
  - Protect runner-owned control directories from being deleted mid-job ([#17535](https://github.com/elizaos/eliza/pull/17535)).  
  - Avoid pruning runners when state can’t be determined ([#17575](https://github.com/elizaos/eliza/pull/17575)).
- **CI smoke-test classifier coverage added** ([#17553](https://github.com/elizaos/eliza/pull/17553))  
  Adds focused tests so intentional LifeOps `activity-signals` failures don’t masquerade as regressions.

### Critical Bug Fixes / Correctness
- **Provider deadlines now cancellation-safe** ([#17490](https://github.com/elizaos/eliza/pull/17490))  
  Fixes unsafe behavior where timeouts could race without aborting underlying work and cache “empty context” as if it were real output.
- **Tool failures now answer honestly** ([#17501](https://github.com/elizaos/eliza/pull/17501))  
  Instead of funneling tool errors into a generic planner fallback, the agent surfaces the real failure mode (more debuggable, and better UX).
- **Time handling correctness** ([#17500](https://github.com/elizaos/eliza/pull/17500))  
  Removes a brittle intent gate so Stage-1 consistently renders `CURRENT_TIME`, addressing cases where the agent could answer with an incorrect date/time.
- **Cloud snapshot safety bound** ([#17180](https://github.com/elizaos/eliza/pull/17180))  
  Aligns snapshot retention with what restore can actually consume—safety improvements that matter under real-world storage and recovery pressure.

### Notable Work in Progress (heads-up)
- **Large repo cleanup / CI hardening refactor opened** ([#17585](https://github.com/elizaos/eliza/pull/17585))  
  This is a “big swing” PR (very large diff) aimed at removing non-essential parts of the repo to match “new direction” priorities. Expect review discussion and possible follow-up breakouts.
- **Fork PR gate timeout issue** remains open ([#17551](https://github.com/elizaos/eliza/issues/17551))  
  The problem: required-check aggregators can time out while workflows are stuck in GitHub’s `action_required` approval state for first-time contributors. A fix here would make first contributions significantly less confusing.

## 3) Community Spotlight (Discord)

### Welcoming new builders (and a clear onboarding need)
In **#💬-coders**, several new members introduced themselves and asked how to get started contributing—especially to **eliza.army**. One key moment: **mochinolabs** asked for starter docs, and **zenithxxs** confirmed documentation exists, but the conversation didn’t include a direct link. Action item for all of us: when onboarding newcomers, point them directly to **https://docs.elizaos.ai** (the channel topic already does, but it helps to repeat it in-thread).

### Community-built tools: Solana safety tooling
**pnllabs_13084** announced a new Solana trading plugin: **`@pnllabs/plugin-pnllabs`** (npm). It provides pre-transaction verification features like wallet trust scoring (based on realized on-chain PnL), token safety checks, cost analysis, and funding forensics. Interesting datapoint from their audit: ~half of tracked “smart money” wallets were *actually losing money*. The plugin includes a free tier (no API key) and paid usage via **x402** pay-per-call.

### Privacy product launch: Coopa v4.0 (testnet)
**nativesatoshi (Selcuk)** shared **Coopa v4.0**, a “zero-trust digital sanctuary” deployed on **Sepolia**, using client-side encryption before storing files/messages on **Irys/Arweave**. The ask: stress-test the architecture and provide UX feedback—great opportunity for community members interested in privacy-by-design patterns.

### Safety reminder
Community members flagged potential **scam accounts** and advised avoiding engagement with suspicious IDs. If you’re unsure whether an account is legit, ask a mod or verify through known roles and message history.

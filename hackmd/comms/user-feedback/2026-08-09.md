### 2) Usage Pattern Analysis (actual vs intended usage)

**Observed actual usage (from feedback):**
1. **Community uses Discord as the primary “status desk”** for token, governance, and repo continuity—rather than for technical support.  
2. **Builders are bifurcating into two groups:**
   - “Normal user agents” (health, research/docs, tax, DIY) aligned with leadership vision.
   - Web3/DeFi agents (DAO governance agent, deterministic impermanent-loss calculator) continuing despite the pivot away from token economics.
3. **Contributors rely heavily on CI + contribution automation (“eliza.army” / evidence gates)**; when these gates fail or are confusing, contribution slows immediately.

**Emerging / unexpected applications:**

- Deploying apps from conversation + custom social feeds (requested by Shaw; aligns with current app-control + UI work).
- DAO/DeFi “auditability” mode: reproducible traces, deterministic calculators (aligns with finance-agent builders).

### 3) Implementation Opportunities (solutions per major pain point; prioritized by impact × difficulty)

#### Pain Point A/B/C: Token fallout + lack of closure + mismatched expectations
**High impact / Low–Medium difficulty**
1. **Publish a permanent “Token Closure & Project Pivot” page** (versioned, timestamped, signed statement).
   - Include: final status (“dead”), what the team will/won’t do, where software continues, and a short FAQ.
   - Mirror it in: docs, Discord pinned post, GitHub org README, and X profile link-in-bio.
   - *Comparable approach:* Mozilla and Kubernetes use formal deprecation/sunset notices with pinned docs and clear “support ends” dates.

2. **Remove/redirect token references from official surfaces** (docs pages, migration/allocation sections, social links to Coingecko).
   - Replace with “Historical (Archived)” section if needed for transparency.
   - *Comparable approach:* Homebrew and Rust routinely mark deprecated docs as “Archived” and prevent them from appearing as current guidance.

3. **Set Discord moderation policy + channel structure to separate “legacy token” from “core dev/product”**
   - One locked announcement thread for token closure; one read-only archive; hard rule: price talk removed from core channels.
   - *Comparable approach:* Many OSS projects create a single “security/advisory” channel and keep general channels technical (e.g., Rust security advisories, CNCF project moderation playbooks).

---

#### Pain Point D: CI/fork contribution friction (action_required polling, contributor tooling breakage)
**High impact / Medium difficulty**
1. **Fail-fast on `action_required` in aggregate gates** (explicit message: “awaiting maintainer approval” + stop polling).
   - Prevents wasting 20–40 minutes of runner time and reduces “false red” checks (issue #17551).
   - *Comparable approach:* GitHub’s own recommended patterns for forks use conditional execution or explicit “needs approval” messaging to avoid dead waits.

2. **Document “supported contributor baseline” (gh CLI, Bun version, OS)** prominently in CONTRIBUTING + contributor-skill docs.
   - The `gh --slurp` incompatibility (#17674) shows real-world mismatch with Ubuntu LTS packages.
   - *Comparable approach:* Kubernetes and Node.js clearly state supported tooling versions and provide a script to verify locally.

3. **Add a “first-time contributor lane”**: minimal checks, plus a bot comment explaining approval mechanics and how to get CI started.
   - Converts confusion into a guided workflow.
   - *Comparable approach:* Rust’s `rustbot` and many repos use bots to guide first-time PR steps and CI approvals.

---

#### Pain Point E: Production reliability (cloud billing/auth warming, voice cold-start)
**High impact / Medium–High difficulty**
1. **Add user-facing degraded-mode messaging** for warming/503 classes (in UI and connector responses).
   - If a request fails due to cache warming, surface “retrying automatically” instead of generic failure.
   - *Comparable approach:* Vercel/Next.js and many cloud SDKs classify retriable errors and auto-retry with clear UI hints.

2. **Expand synthetic probes + public status indicators** for key surfaces (inference success rate, voice session start).
   - Tie to release gates; ensure “alternating failure” patterns are detected before prod (as in #17745/#17865).
   - *Comparable approach:* Stripe’s API has robust health checks and dashboards; SRE-style SLIs prevent regressions from shipping silently.

3. **Voice parity test suite**: enforce that voice and text channels share response grammar where intended (e.g., filler/ack behavior).
   - *Comparable approach:* Cross-channel parity tests are common in chat products (web/mobile parity harnesses).

---

#### Pain Point F/G: Integration + UX direction confusion (Web3 hidden vs Web3 builders; “normal users” need flows)
**Medium impact / Low–Medium difficulty**
1. **Publish a “Supported Web3 Surfaces” compatibility matrix**
   - What’s supported internally, what’s intentionally invisible, what is deprecated, and how to build safely (preview-first, no silent writes).
   - *Comparable approach:* OpenZeppelin documents threat models and “safe defaults” for on-chain integrations.

2. **Ship 3–5 curated “starter agents” as reference apps**
   - Research assistant (docs), health habit coach, DIY planner, tax prep checklist—each with a “Day 1 success” path.
   - *Comparable approach:* LangChain and similar frameworks succeed by shipping opinionated templates that mirror real usage.

3. **Add “auditability mode” hooks for deterministic finance agents**
   - Provide trace outputs / reproducible calculations option for DeFi builders (responds to faouzi_122’s audit-trace question).
   - *Comparable approach:* Database migration tools and cryptographic libs often support “explain/trace” modes for verification.

### 6) Feedback Collection Improvements (channels effectiveness + missing segments)

**Current channels:**
- **Discord:** high volume, high emotion, low structure; currently dominated by token closure discussion.
- **GitHub issues/PRs:** highly structured for engineering, but not capturing end-user needs except indirectly (bugs, CI pain).

**What’s working:**
- GitHub templates and evidence gates produce high-quality engineering artifacts when contributors can get past CI friction.

**What’s not working:**
- Discord lacks a structured path to convert complaints/questions into actionable tickets.
- “Normal user” feedback (non-developer, non-crypto) is underrepresented; most visible voices are token holders and builders.

**Concrete improvements:**
1. **Add a lightweight “User Pain” intake form** (GitHub Discussions or a form that creates labeled issues):
   - Fields: goal, what they tried, where it failed, logs/screens, channel (text/voice/web), severity.
2. **Monthly end-user office hours / usability tests** focused on the app onboarding + core agent flows (recorded findings).
3. **Segment feedback channels**:
   - `#token-archive` (read-only + canonical links)
   - `#getting-started` (onboarding Qs)
   - `#agent-showcase` (templates/use cases)
   - `#dev-help` (CI/runtime)

**Underrepresented segments:**
- Non-crypto end users (target audience per leadership messaging).
- Integrators who want “invisible Web3 rails” without crypto UX (product/SDK feedback needed).
- Mobile/voice-first users (only indirectly represented via engineering fixes).

## 1) Pain Point Categorization (Top recurring 5–7)

### 1) **Technical Functionality — Cloud agent provisioning reliability regressions (P0)**
**Frequency/Severity indicators**
- 1 of the top 5 surfaced GitHub issues is a quantified P0 provisioning regression: **16.1% hard failure** rate since 2026-08-06 (#18052), with a **~52 minute** failure feedback loop.
- Additional related thread: staging test coverage conflation with prod defaults (#18076).

**What users experience**
- Agent creation intermittently fails; failures can block future provisioning for the same org until fixed (#18052 references permanent lockout behavior pre-#17924).
- Users wait a long time before learning something failed (watchdog/retry loop → ~52 min).

**Concrete implementation opportunities (prioritized)**
1) **High impact / Medium difficulty:** Reduce time-to-failure-notification from ~52 min to <2–5 min  
   - Add early “capacity/placement preflight” + fast-fail on known 409/fence deadlock signatures (ties to #17924 + #18052).
2) **High impact / Medium difficulty:** Fix autoscaler ceiling/configurability + pre-warm behavior  
   - #18052 notes autoscaler gated by `maxNodes` hardcoded to 12 while 14 enabled; add env override + correct gating.
3) **High impact / Higher difficulty:** Add “provisioning invariants” monitoring + rollback automation  
   - Establish SLO alerts (failure rate, enqueue 409s, fence count growth, placement free slots) and automated rollback to last known-good daemon build.

**How similar projects address it**
- Kubernetes-based platforms often use admission controllers + preflight capacity checks to fail fast (clear, actionable errors) rather than letting async jobs time out.
- Managed CI platforms (e.g., Render/Fly-style deploys) surface “capacity unavailable” instantly and provide queue position/ETA.

### 2) **Performance — Auth/login first-interaction latency gated by provider list endpoint**
**Frequency/Severity indicators**
- 1 of top 5 surfaced issues: sign-in buttons gated by `/steward/auth/providers` taking **up to 4.7s in production** (#18049).

**What users experience**
- Login page paints quickly (FCP ~92ms) but cannot act until provider list returns; perceived as “site is slow/broken” at the first impression moment.

**Concrete implementation opportunities (prioritized)**
1) **High impact / Low–Medium difficulty:** Cache provider list with explicit TTL + safe invalidation  
   - If providers change only at deploy/config time, serve cached results (and document propagation).
2) **Medium impact / Medium difficulty:** Split “thin” auth bootstrap path from full app bootstrap  
   - Ensure the endpoint is served by a minimal code path with no upstream dependency chain (Worker-local response).
3) **Medium impact / Medium difficulty:** Add client-side optimistic rendering for common providers  
   - Render buttons for the default set immediately; reconcile with server response to avoid “dead” UI.

**How similar projects address it**
- NextAuth/Auth0-like flows commonly ship provider config as static JSON at build time or edge-cached with aggressive TTLs, so login stays interactive.

### 3) **Integration — Telegram onboarding/identity binding breaks end-to-end**
**Frequency/Severity indicators**
- 1 of top 5 surfaced issues: Telegram system bot onboarding is “dead” and does not bind Cloud identity (#17888).

**What users experience**
- Telegram DM returns onboarding URL, but:
  - URL points to a host that doesn’t reliably boot (`eliza.app/get-started` at the time of report).
  - Even when loaded via authenticated host as workaround, Telegram identity is not durably linked; user gets onboarding loop again on next DM.

**Concrete implementation opportunities (prioritized)**
1) **High impact / Medium difficulty:** Make Telegram linking cryptographically verifiable (server-validated Telegram proof)  
   - Do not treat browser auth as proof of Telegram sender; require signed Telegram payload/HMAC validation and persist canonical sender ID.
2) **High impact / Low difficulty:** Fix canonical onboarding URL configuration for Telegram bot  
   - Ensure `ELIZA_ONBOARDING_APP_URL` resolves to a working host that serves correct JS content types and caching behavior (#17888 notes MIME/caching inconsistencies).
3) **Medium impact / Medium difficulty:** Add E2E tests for “DM once → link → DM routes to agent”  
   - Include negative cases (expired token, replay, sender mismatch) as explicitly listed in #17888 acceptance criteria.

**How similar projects address it**
- Slack/Discord OAuth link flows typically complete linking in-chat with a signed “return to chat” token bound to the platform user ID (avoids “browser authenticated ≠ platform identity” confusion).

### 4) **Documentation / QA Process — Staging vs production coverage confusion**
**Frequency/Severity indicators**
- 1 of top 5 surfaced issues: a “green” live Cloud E2E job **silently targets production** by default and does not prove staging (#18076).

**What users experience**
- Maintainers/operators can believe staging is verified when only production is tested, leading to regressions reaching users or lingering staging breakages.

**Concrete implementation opportunities (prioritized)**
1) **High impact / Medium difficulty:** Separate staging/prod workflows with explicit base URLs + assertions  
   - Fail closed unless the resolved host matches `api-staging...` for staging lane.
2) **High impact / Low difficulty:** Add environment labeling to artifacts + job names  
   - Prevent “coverage inference” from a single lane.
3) **Medium impact / Medium difficulty:** Provision staging-scoped secrets + test credential route  
   - #18076 notes missing staging Environment secret inventory for required API keys.

**How similar projects address it**
- Many platforms enforce “environment-specific deploy + test contracts” (e.g., Vercel preview vs production) with hard-coded origin assertions and separate credentials.

## 2) Usage Pattern Analysis (Actual vs intended)

### Observed “actual usage”
- **Cloud-hosted onboarding and agent provisioning** is a dominant operational focus (issues #18052, #18076, #18049).
- **Messaging-first entry** (Telegram/iMessage/Discord DM → connect → agent replies) is a primary real-world flow (#17888 and related onboarding continuity work referenced across the repo activity).
- **Voice as a production feature** is positioned as important (weekly summary notes real-time voice in production; community member satya.manhas expects multi-platform apps).
- **Community discussions drift into tokenomics/governance** when product comms are quiet (Discord 08-13).

### Gaps vs intended usage
- Intended: smooth onboarding across surfaces; actual: identity binding and environment routing issues cause loops (Telegram onboarding repeats).
- Intended: staging validates changes; actual: staging lane can be “green” while hitting prod defaults (#18076).

### Emerging/unexpected use cases
- **DAO/crypto/payments collaboration** interest (Zeroclaw community call; paralens.ai shared) suggests users want deeper integration with on-chain analytics and payments tooling.
- **Brand/naming experimentation** (rename suggestion “XOS”) is likely lighthearted, but signals attention to identity/positioning.

### Feature requests aligned to usage patterns (from signals)
- Cross-platform chat + voice parity (Discord expectations of Android/iOS/Mac/PC apps).
- Multi-channel community comms (Telegram chat request), though needs clear stance to avoid support fragmentation.

## 6) Feedback Collection Improvements

### Current channel effectiveness
- **GitHub issues are highly actionable** (quantified metrics, repro steps, acceptance criteria).
- **Discord is currently low-signal for product feedback** on some days (08-15 had no technical content), and important questions may not be answered (08-14 Telegram channel query).

### Improvements to gather more structured feedback
1) Add a **single pinned Discord intake link**: “Report a bug / onboarding loop / provisioning failure” → GitHub issue form with required fields (environment, platform, host, timestamps).
2) Add **in-product “Report onboarding problem”** button on `/login` and `/get-started` that exports redacted diagnostics (host, request IDs, timing).
3) Run a **monthly structured survey** for:
   - onboarding success rate (by connector),
   - login perceived latency,
   - provisioning success rate and time-to-agent.

### Underrepresented segments whose feedback is missing
- **Non-Discord users** (Telegram/iMessage-first users) who may churn without filing GitHub issues.
- **Mobile-only users** (Android/iOS) given expectations of app support but limited direct feedback in this dataset.
- **Framework builders (non-crypto)**: Discord discourse skewed toward token/governance; need clearer channel for OSS/framework adoption feedback.

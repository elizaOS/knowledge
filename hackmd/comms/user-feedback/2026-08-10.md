### Data sources referenced
- Discord daily summaries: 2026-08-07, 2026-08-08, 2026-08-09
- GitHub issues/PR context (notably open issues filed/active during 2026-08-07 to 2026-08-09)

## 1) Pain Point Categorization (top recurring friction areas)

### 1) **Community — Token status, governance, and trust rupture**
**Frequency/Severity:** Very high / High. Token discussion appears in **3/3 Discord days (100%)** with repeated unanswered questions (e.g., “Who currently controls the token?” asked multiple times by the same user across the day).  
**What users report**
- Persistent confusion about **who controls the token now** (Discord 2026-08-09; crx92 asked twice).
- Anger/frustration about **token rebrand → abandonment** and lack of closure (Discord 2026-08-08).
- Requests for a **formal transfer process** (new legal entity; “work with Shaw”) but no concrete resolution by end of day (Discord 2026-08-09).
- Scammer presence noted alongside token discussion, compounding trust issues (Discord 2026-08-09; Vicorico).

**Most affected users**
- Token holders and newcomers who discover the community via token-related content/interviews (Coindesk mention).

---

### 2) **Integration — Messaging connector onboarding breaks (Telegram handoff + identity binding)**
**Frequency/Severity:** Medium / Critical (blocks core “message the agent from X” use case).  
**What users report**
- Telegram system-bot onboarding path returns an onboarding URL that **fails to boot reliably** and does **not bind Telegram identity** to Cloud account; second DM repeats onboarding instead of routing to agent (**GitHub #17888**).
- Even when workarounds exist (switching host), the flow lacks durable, secure identity linking.

**Most affected users**
- Users adopting ElizaOS as a cross-channel agent (Telegram/iMessage/WhatsApp style experience) rather than as a dev framework.

---

### 3) **Performance / Technical Functionality — Cloud agent provisioning reliability regression**
**Frequency/Severity:** Medium / Critical (blocks onboarding and causes long “silent failure” waits).  
**What users report**
- Production provisioning regressed to **16.1% hard failure** after a clear streak: “0 failures across 63 jobs” → “20 failed / 124 jobs” (**GitHub #18052**).
- Failure mode is user-hostile: ~**52 minutes** to notify user when something goes wrong (watchdog/retry loop), and some errors can cause **permanent lockout** until a fix lands (referenced in #18052 via #17924).

**Most affected users**
- New Cloud users and anyone expecting “chat-to-agent-in-under-2-min” onboarding.

---

### 4) **Performance / UX — Login screen “time-to-first-action” gated by slow providers endpoint**
**Frequency/Severity:** Medium / High (first impression + conversion impact).  
**What users report**
- Login UI paints fast but is non-interactive while waiting on `/steward/auth/providers`, taking **up to 4.7s in production** (**GitHub #18049**).
- The sign-in buttons are entirely gated behind that endpoint, so the user cannot proceed.

**Most affected users**
- New users, mobile users, and anyone arriving from public links who expects instant sign-in options.

---

### 5) **Technical Functionality / QA — Staging vs production coverage gaps and environment drift**
**Frequency/Severity:** Medium / High (creates false confidence; slows releases).  
**What users report**
- “App Live E2E” job silently tests **production by default**, leaving staging path unproved; missing base URL override and missing staging secrets (**GitHub #18076**).
- Confusion about what is “actually tested” vs “assumed tested” (staging auth handoff, provisioning, chat reply).

**Most affected users**
- Maintainers/releasers and contributors relying on CI signals; indirectly affects all users via regressions.

---

### 6) **Documentation / UX — “Is there an iPhone app?” distribution confusion**
**Frequency/Severity:** Low / Medium (recurs as newcomer question; blocks trial).  
**What users report**
- New user asks whether ElizaOS is available on the **App Store** and runnable on **iPhone**, stating they can’t find it (Discord 2026-08-09; Vicorico).
- This indicates mismatch between perceived “product” vs actual distribution model (web/desktop/dev framework).

**Most affected users**
- Non-technical/newcomer users entering through viral/community channels.

---

### 7) **Community — Moderation burden + scam risk perception**
**Frequency/Severity:** Low / Medium, but reputationally important.  
**What users report**
- “Scammers in the community” flagged by a newcomer (Discord 2026-08-09).
- Token turmoil amplifies scam risk and increases moderation load.

**Most affected users**
- Newcomers and passive observers deciding whether to trust the project.

## 2) Usage Pattern Analysis (actual vs intended usage)

### Observed real-world usage patterns
1. **“Consumer agent OS” expectations** are rising: users ask about iPhone availability and everyday assistants (health/fitness tracking, tax optimization, research assistant, DIY/construction helper) (Discord 2026-08-07/08/09).  
   - This is beyond “open-source framework” expectations; users want **a product**.

2. **Connector-first workflows** (Telegram/Discord/iMessage style) appear central:
   - The Telegram onboarding/identity-binding issue (#17888) shows users expect “DM the bot → sign in → it’s your agent”.

3. **Web3/DeFi remains a strong community gravity well** even as leadership pivots away from token economics:
   - Examples: deterministic impermanent-loss calculator discussion (Discord 2026-08-07), DAO-focused agent idea + large governance repo shared, new members wanting Web3 agent tools (Discord 2026-08-08).

4. **Community still uses Discord as a primary “support desk”** even for product questions (App Store, token control), which creates repeated Q/A churn and unresolved loops.

### Emerging / unexpected applications
- **Deterministic finance math modules** (O(1) impermanent loss calculator) suggesting demand for “auditable computation traces” in agents used for financial decisions (Discord 2026-08-07).
- **“ElizaOS as a native phone OS” narrative** (partnership mentioned by Shaw) raises user expectations for mobile availability and stability, even if not shipped yet.

### Feature requests aligned with actual usage
- **Stable, secure connector identity linking** (Telegram and others) and a consistent onboarding funnel.
- **End-user app experiences** (health/research/personal assistant) that hide Web3 complexity while preserving infrastructure.

## 3) Implementation Opportunities (solutions per major pain point)

Below, each pain point includes 2–3 implementable solutions, prioritized by **Impact** and **Difficulty**.

### A) Token governance/status confusion (Community/Documentation)
1) **Publish a single canonical “Token Status & Governance FAQ”** pinned across Discord + GitHub + website  
- **Impact:** High | **Difficulty:** Low  
- Must explicitly answer: token is dead vs community-managed, who controls contracts/keys (if any), what the project does/does not promise.  
- Similar approach: many open-source projects post “Security/Incident FAQ” after an event (e.g., Kubernetes postmortems; OpenSea/bridge incident FAQs).

2) **Create a dedicated, quarantined channel + moderation policy for token talk**  
- **Impact:** Medium | **Difficulty:** Low  
- Aligns with Shaw’s stated desire to ban price talk while still providing a containment zone for legal/closure questions.

3) **If any transfer is real: define a public checklist for legal-entity takeover** (even if “not happening”)  
- **Impact:** Medium | **Difficulty:** Medium  
- Converts repeated “who controls it?” into a trackable process (owner-of-record, multisig, legal entity creation, signing authority, timeline).

---

### B) Telegram onboarding + identity binding failures (Integration/Technical Functionality)
1) **Make onboarding host canonical and enforced** (stop sending users to a host that can’t boot)  
- **Impact:** High | **Difficulty:** Medium  
- The #17888 root cause explicitly points to `ELIZA_ONBOARDING_APP_URL` being overridden to `https://eliza.app`. Enforce a single supported host for onboarding assets with correct MIME/caching.

2) **Add a secure “signed identity proof” step for Telegram linking (server-validated)**  
- **Impact:** High | **Difficulty:** Medium–High  
- Ensure “browser signed in” ≠ “owns Telegram sender”.  
- Similar to Slack/Discord OAuth linking flows: require provider-signed payload validation server-side before persisting identity.

3) **Add connector E2E tests for “DM twice” contract**  
- **Impact:** Medium | **Difficulty:** Medium  
- Tests should assert: first DM gives onboarding once; after linking, second DM routes to assigned agent (explicitly in #17888 acceptance criteria).

---

### C) Provisioning reliability regression + long failure notification (Performance/Technical)
1) **Shorten time-to-failure notification from ~52 minutes to <2 minutes**  
- **Impact:** High | **Difficulty:** Medium  
- Add earlier “fast-fail” detection and user-facing status updates (queue capacity, placement failure, fence deadlock).  
- Similar approach: managed platforms (Render/Fly.io/Heroku) surface provisioning status quickly and provide immediate actionable errors.

2) **Fix autoscaler gate + pre-warm capacity** (based on #18052 findings)  
- **Impact:** High | **Difficulty:** Medium  
- Remove hardcoded `maxNodes=12` if fleet has 14 enabled; add env override; ensure proactive autoscaler can scale up, not only drain.

3) **Eliminate “permanent lockout” after provisioning error**  
- **Impact:** High | **Difficulty:** Medium  
- Ensure error rows don’t block future onboarding provisioning; add self-healing cleanup and safe retry paths (referenced by #18052 / #17924).

---

### D) Login providers endpoint latency gating sign-in (Performance/UX)
1) **Cache `/steward/auth/providers` with explicit TTL + safe invalidation**  
- **Impact:** High | **Difficulty:** Low–Medium  
- Provider list changes at deploy/config time, so it should be cacheable.  
- Similar pattern: NextAuth/Clerk-style provider configuration is typically build/deploy-time, not per-request.

2) **Render default provider buttons immediately, then reconcile**  
- **Impact:** Medium | **Difficulty:** Medium  
- Don’t block first action on the endpoint; optimistically show common providers and disable only if response removes them (with strict “fail closed” semantics for removed providers).

3) **Instrument p95/p99 for the endpoint and add a perf budget gate**  
- **Impact:** Medium | **Difficulty:** Low  
- Adds continuous visibility so regressions don’t ship unnoticed.

---

### E) Staging/prod drift in CI and QA signals (Technical Functionality)
1) **Split jobs into explicit “staging” and “production” lanes with asserted base URLs**  
- **Impact:** High | **Difficulty:** Medium  
- #18076 outlines exact missing knobs (`ELIZAOS_CLOUD_BASE_URL`, secrets). Add “fail closed unless host matches”.

2) **Add environment-scoped secrets inventory checks**  
- **Impact:** Medium | **Difficulty:** Low  
- CI should fail if staging lane is enabled but required staging secrets are missing.

3) **Report tested artifact provenance** (deployed app vs local renderer)  
- **Impact:** Medium | **Difficulty:** Medium  
- Prevents conflating “local UI smoke” with “deployed staging path”.

---

### F) iPhone/App Store confusion (Documentation/UX)
1) **Add a “Where can I run ElizaOS?” landing doc** (Web, Desktop, iOS/Android status, “not in App Store yet” if true)  
- **Impact:** Medium | **Difficulty:** Low  
- Link it from Discord welcome message and /help bot command.

2) **In-product/website copy: avoid “OS” implications without qualifiers**  
- **Impact:** Medium | **Difficulty:** Low  
- If “native OS” partnerships are aspirational, label them clearly as roadmap to reduce false expectations.

---

### G) Scammer/trust concerns (Community)
1) **Add a security banner + reporting flow** (how to verify official links, where to report scams)  
- **Impact:** Medium | **Difficulty:** Low  
2) **Tighten link-posting rules in high-traffic channels** (slow mode, link previews restricted, verified roles)  
- **Impact:** Medium | **Difficulty:** Low–Medium

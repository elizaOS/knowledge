## 3) Implementation Opportunities (solutions per major pain point)

### 1) Unanswered support questions (Community / Documentation)
**Solutions (prioritized):**
- **High impact / low–medium difficulty:** Add a dedicated “Help Desk” flow in Discord:
  - Convert Q&A into a **Forum channel** with required tags (Cloud, Plugins, On-chain, Mobile, Docs).
  - Add a bot that prompts: “Have you searched docs? If not, here are top links; if unresolved, auto-create a GitHub Discussion/Issue draft.”
- **High impact / low difficulty:** Publish a pinned “How to get help” message:
  - What belongs in Discord vs GitHub issues; expected response times; how to include logs/repro steps.
- **Medium impact / medium difficulty:** Create a rotating “triage captain” volunteer role (weekly) to ensure **zero unanswered threads >24h**.

**Comparable approaches:** Kubernetes and Rust communities use forum/Q&A structure + triage rotations; many OSS projects rely on issue templates + Discord-to-GitHub escalation bots.

---

### 2) Scam warnings and moderation ambiguity (Community)
**Solutions:**
- **High impact / low difficulty:** Add a pinned anti-scam playbook:
  - “No DMs from staff,” verified maintainer list, how to report, how to verify links.
- **High impact / medium difficulty:** Automod + reporting workflow:
  - Auto-flag brand-new accounts posting payment links; require minimum account age for certain channels.
- **Medium impact / medium difficulty:** Public “moderation outcomes” lightweight logging:
  - When scam IDs are reported, a mod note confirms action taken (timeout/ban/false alarm) to restore trust.

**Comparable approaches:** Ethereum/DeFi Discords commonly use strict link controls + mod-logged actions to reduce repeated scam cycles.

---

### 3) LP3 mobile UI regressions (UX/UI)
**Solutions:**
- **High impact / medium difficulty:** Add a “small viewport contract” visual gate:
  - A dedicated Playwright suite targeting **1080×1240** (and smaller) with assertions for hit-target presence (non-zero bounding boxes) for Notifications and Launcher.
- **High impact / low difficulty:** Replace hard caps like `max-height: 40%` with responsive constraints:
  - Use `clamp()` or content-measured layout; introduce device-class breakpoints for short panels.
- **Medium impact / medium difficulty:** Introduce a “demo build safety” branch/tag:
  - Ensure demo-day builds have a protected baseline; regressions require explicit sign-off.

**Comparable approaches:** React Native and mobile-web teams often enforce “golden screenshots” for a few worst-case viewports to prevent exactly this class of regression.

---

### 4) Cloud vs direct provider ownership confusion (Technical Functionality)
**Solutions:**
- **High impact / medium difficulty:** Make provider arbitration explicit and inspectable:
  - At runtime boot, log a **human-readable routing table**: capability → provider → reason (direct route, cloud-managed, stripped).
  - Add a `runtime self-status` view showing effective providers loaded vs configured.
- **High impact / medium difficulty:** Tighten plugin-collector policy:
  - Preserve the provider plugin that owns any explicitly routed capability; strip only unrelated local surfaces (as #17516 requests).
- **Medium impact / low difficulty:** Documentation: “Hybrid Cloud routing: supported patterns”
  - Provide canonical examples for OpenAI/Cerebras/Ollama/local + Cloud-managed capabilities.

**Comparable approaches:** Temporal and HashiCorp tools expose “effective configuration” views to reduce invisible precedence rules.

---

### 5) CI gate gaps causing regressions (Performance / Reliability)
**Solutions:**
- **High impact / low–medium difficulty:** Add plugin unit tests to `develop` PR required checks (scope by changed paths if needed).
  - Validate with a deliberate-break test as requested in #17550 (red/green proof).
- **Medium impact / medium difficulty:** Establish “risk-based gates”:
  - If `packages/ui` or mobile shells change, require viewport visual suite; if `plugins/*` changes, require plugin tests.
- **Medium impact / low difficulty:** Post-merge monitoring dashboard for `develop`:
  - A single page showing current `develop` health + last green SHA to discourage building on red heads.

**Comparable approaches:** Chromium and large monorepos rely on presubmit suites + per-directory ownership/risk gates.

---

### 6) On-chain bridging and funding flows unclear (Integration / Documentation)
**Solutions:**
- **High impact / low difficulty:** Add a “Funding & Bridging for agents” doc page:
  - List supported bridges/paths for common pairs (e.g., Base→Solana), including security caveats.
- **Medium impact / medium difficulty:** Community-maintained “Known Good Integrations” registry:
  - A markdown table (or simple site page) with last-verified dates and maintainers.
- **Medium impact / low difficulty:** Route these questions to specialists:
  - A Discord role ping (“On-chain integrators”) + dedicated thread for bridging questions.

**Comparable approaches:** Solana and Polygon ecosystems maintain “official bridge guidance” pages to reduce repeated Q&A.

## 4) Communication Gaps (expectations vs reality)

1) **“Ask in Discord” expectation vs actual response rate**
   - In this slice, **100% of help questions remained unanswered**, implying Discord is not functioning as reliable support without structure.
2) **Official status ambiguity**
   - Brief “not official” clarifications suggest users may treat all announcements as endorsed. Need clear labeling: “community project” vs “core elizaOS.”
3) **Cloud/hybrid routing expectations**
   - Users expect explicit direct-provider routes to win; current behavior can contradict that, and the system provides insufficient visibility into why.

**Recommended comms improvements:**
- Add an “Official / Community” badge system for Discord announcements (channel-specific or bot-enforced prefixes).
- Publish “Support SLA expectations” (even if informal) and the correct place to file bugs vs ask usage questions.
- Provide a one-page “Cloud vs Local vs Hybrid” mental model with precedence rules and examples.

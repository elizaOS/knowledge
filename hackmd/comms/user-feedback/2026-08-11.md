## 2) Usage Pattern Analysis (Actual vs intended)

### Observed real-world usage (from feedback)
1. **Messaging-first onboarding** is a primary entry path (Telegram system bot; implied iMessage/WhatsApp gateway references in issues/PR summaries). Users expect “DM bot → authenticate → bot remembers me → messages route to my agent”.
2. **Hosted Cloud as the “product front door”**: Users judge elizaOS by `app.elizacloud.ai` login speed, provisioning success, and time-to-first-reply (issues #18049, #18052).
3. **Agents as operational tools**, not demos: transportation agent implementation (Discord 2026-08-10), plus rising interest in “Web3 agent tools” (Discord 2026-08-08).
4. **Community still arrives via token channels** and expects token-related roadmaps, governance clarity, and event integrations—despite the project pivoting away from token economics.

### Emerging / unexpected use cases
- **Event activation** (“integrate token at Jeju”) indicates continued offline/community marketing assumptions that conflict with the “token dead” status and software-only pivot.
- **Web3 tool builders** joining post-token turbulence suggests elizaOS still has pull as an agent framework even when token narrative is negative—if onboarding and docs are strong.

### Feature requests implied by usage patterns
- “Connector-first onboarding that actually binds identity” (Telegram today; generalizable to other connectors).
- “Hosted-first reliability guarantees” (explicit SLO-like targets for login/provisioning/first reply).
- “Reference implementations” (transportation/logistics agent blueprint, Web3 agent tool starter kits).

## 3) Implementation Opportunities (Concrete solutions per major pain point)

### A) Token status/governance confusion (Community/Docs)
**High impact / low-medium difficulty**
1. **Publish a canonical “Token Status & Project Scope” page** linked everywhere (Discord pinned message, website banner, GitHub README). Include:
   - Current status (“dead”/unsupported), what the team will/won’t do, and where software roadmap lives.
   - FAQ: exchange listings are not endorsements; no event integrations planned unless explicitly announced.
   - A short timeline (rebrand attempt → settlement → pivot).
2. **Governance clarity post**: explicitly answer “who controls what” (even if answer is “unknown / in transfer”) and list the steps being taken (or not taken).
3. **Separate channels**: create a dedicated Discord category for token-holder discussion + moderation guidance to keep #discussion usable for builders.

**Comparable approaches:**  
- Projects that sunset tokens (or discontinue products) often use a single immutable “status page” + pinned comms (e.g., deprecation notices in OSS foundations; “End of Life” pages in major frameworks).

---

### B) Provisioning reliability regression (Technical/Performance)
**Very high impact / medium difficulty**
1. **Fail-fast user feedback loop**: reduce the failure-path notification from ~52 minutes to <2 minutes by:
   - Introducing early, user-visible state transitions (“capacity constrained”, “retry scheduled”, “action needed”) rather than silent watchdog timeouts.
   - Proactive preflight checks before enqueue (capacity, fences, autoscaler state).
2. **Autoscaler correctness + configurability**:
   - Fix the hardcoded `maxNodes` logic so proactive autoscaling can scale up (issue #18052 notes `maxNodes` hardcoded to 12 while 14 enabled).
   - Add environment overrides + alerts when configured limits prevent scale-up.
3. **Fence lifecycle cleanup + deadlock prevention**:
   - Add automatic retirement/GC of replacement-cleanup fences; include a dashboard metric “active fences” with paging thresholds.

**Comparable approaches:**  
- Kubernetes cluster autoscaler patterns: explicit scale limits, metrics, and “pending pods” surfaced immediately; fence-like locks typically have TTLs + GC jobs.

---

### C) Login/auth provider endpoint latency gating sign-in (UX/Performance)
**High impact / low-medium difficulty**
1. **Cache `/steward/auth/providers`** with a clear TTL and invalidation story (providers change infrequently).  
2. **Ship a “default button skeleton” immediately** and progressively enhance once providers load; keep at least 1 primary method available (e.g., email magic link) if provider list is late.  
3. **Instrument p95/p99 latency** and set a budget (issue target suggests p95 <300ms). Add alerting when it regresses.

**Comparable approaches:**  
- Auth frameworks commonly cache provider metadata (e.g., config-driven provider lists) and avoid blocking TTI on remote metadata fetch.

---

### D) Connector onboarding + identity binding failures (Integration/Technical)
**High impact / medium difficulty**
1. **Make connector binding cryptographically provable by default**:
   - Telegram: require server-validated Telegram proof (HMAC signed payload) before linking, as requested in #17888.
2. **Canonicalize onboarding host + enforce it**:
   - Ensure bot links point to a stable, supported host (`app.elizacloud.ai` or explicit connector onboarding host), not marketing/waitlist surfaces.
3. **End-to-end tests per connector**:
   - “First DM → onboarding link → auth → second DM routes to agent” as a required live smoke test (staging and prod).

**Comparable approaches:**  
- Slack/Discord bot ecosystems: OAuth install flow binds workspace/user IDs server-side and verifies state/nonce; repeated onboarding loops are prevented by durable external identity linkage.

---

### E) Staging vs production test coverage illusions (Docs/DevEx)
**Medium-high impact / medium difficulty**
1. **Split “prod evidence” and “staging evidence” jobs** with explicit base URL assertions (mirroring the acceptance criteria in #18076).  
2. **Require environment secrets to exist (or fail closed)** for staging tests so green cannot happen without staging credentials.  
3. **Surface “what was tested” in CI summary**: resolved hostnames, whether it hit deployed artifact vs local renderer.

**Comparable approaches:**  
- Many CI systems print and assert target endpoints (“ENV under test”), and treat missing environment-specific secrets as a hard skip/fail rather than silently defaulting.

---

### F) Turn real successes into replicable adoption (Docs/Community)
**High leverage / low difficulty**
1. **“Agent Case Study” template** (Discord + GitHub Discussions): problem, tools/plugins used, runtime choice, deployment, gotchas, metrics.  
2. **Request a follow-up from 0x_cup** (transportation agent): architecture diagram + minimal repo snippet + what worked/what hurt.  
3. **Publish 2–3 reference blueprints**: transportation/logistics, Web3 monitoring/ops agent, and “connector-first support bot”.

**Comparable approaches:**  
- OSS frameworks (e.g., web frameworks) grow via “real apps” galleries and “cookbook” patterns; concrete examples reduce docs burden and support load.

## 4) Communication Gaps (Expectations vs reality)

### Key mismatches observed
1. **Token expectations vs software reality**: Users still ask about token integrations (Jeju) and governance while leadership states token is dead and project is decoupled. The absence of a single canonical statement causes repeated loops and escalating frustration.
2. **“Green CI” ≠ “staging is safe”**: Contributors reasonably assume a passing Cloud E2E implies staging coverage, but defaults route to production unless explicitly overridden (#18076).
3. **“Bot gave me a link” ≠ “my identity is linked”**: Users interpret successful browser login as completion of connector binding, but without signed external proof the system must not treat it as linked (#17888).

### Recurring questions indicating onboarding/doc gaps
- “Who controls the token?” (asked multiple times; no authoritative answer)
- “What should we do about the current situation?” (strategic ambiguity)
- “Has anyone successfully built an agent with elizaOS?” (answered once, but without actionable detail)
- “Which exchanges list the token?” (repeated fact-sharing instead of product-building focus)

### Suggested comms improvements
- Add a **“Start Here (Builders)”** flow that redirects token-related discussions to a separate page/channel and immediately presents the software roadmap + onboarding steps.
- Add a **“Hosted reliability status”** section (login latency, provisioning success rate, incident notes) so users don’t infer health from token price or rumors.

## 6) Feedback Collection Improvements

### Current channel effectiveness
- **Discord**: high volume, but token discourse dominates and drowns build/product feedback; questions often go unanswered or loop.
- **GitHub issues**: extremely actionable when filed by power users (measured metrics, clear acceptance criteria). However, this is skewed toward advanced contributors.

### Improvements for more structured, actionable feedback
1. **Add a lightweight in-app “Report an issue”** that auto-attaches:
   - host (app vs staging), endpoint timing, provisioning job ID, connector type, and anonymized trace IDs.
2. **Standardize “Hosted UX bug” template** (parallel to existing bug templates) emphasizing:
   - time-to-first-action, time-to-first-reply, and “what did the user see”.
3. **Monthly “State of Hosted Reliability” post** with the top 3 regressions + resolved items; invites targeted feedback.

### Underrepresented segments whose feedback is missing
- **Non-Discord users** evaluating via the hosted app (likely churn without reporting).
- **Enterprise/team adopters** (identity, governance, compliance concerns) — current signals are mostly from OSS power users.
- **Connector-only users** (Telegram/iMessage) who may never reach GitHub to file issues.

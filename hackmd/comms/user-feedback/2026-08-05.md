### 2) Usage Pattern Analysis (Actual vs intended usage)

#### Observed actual usage
- **Discord is functioning as:**
  1) a **token status/market sentiment forum** (dominant thread),
  2) a **newcomer onboarding help desk** (docs/start-here questions),
  3) an **ad-hoc support channel** for financial/deposit issues (high-risk).
- **GitHub is functioning as a contributor pipeline optimization surface**, especially around CI gates and the **eliza.army / contribute-to-eliza skill** workflow.

#### Likely intended usage (inferred from repo initiatives)
- elizaOS aims to be a **cross-device open-source agent platform** (iPhone/Android/browser/desktop/OS mentions) with a structured contribution pipeline (leaderboard/skill, evidence gates).

#### Emerging / unexpected use cases
- **Compute-to-contribution workflow** is becoming central (eliza.army skill/leaderboard). Users are effectively “using the platform” by automating contribution selection and validation, which creates a new class of UX: *developer automation UX*.
- **Public expectation management** is now a product surface: the community treats token and app-roadmap messaging as part of “the UX” of elizaOS.

#### Feature requests aligned with real usage patterns
- A **single canonical “Start Here”** that routes to: contribute (skill), build/run, and community norms (public support rules).
- A **verified support pathway** for account/deposit issues to reduce scam exposure.
- CI changes to **fail fast and explain** instead of timing out (fork PR gating).

### 3) Implementation Opportunities (Concrete solutions, prioritized)

#### Pain Point A: Roadmap clarity & token ambiguity (Community)
**High impact / Low–Medium difficulty**
1) **Publish a short “Token & Project Scope” policy page** (versioned, linkable) answering:
   - Is the token part of elizaOS product plans? If yes: what is in-scope (utility, governance, none yet) and what is explicitly out-of-scope.
   - If “token development phase is complete,” define what that means operationally (no new contracts? no utilities? no marketing?).
   - Mirror it as a pinned Discord post + GitHub Discussion.
   - *Comparable pattern:* many OSS projects maintain “Project Status / Roadmap” pages (e.g., Rust RFC status pages; Kubernetes enhancement tracking) to reduce rumor-driven support load.
2) **Replace “soon” with milestone-based updates** (even if coarse): “in internal testing,” “beta window,” “public preview criteria,” etc.
3) **Create an “Official Statements” channel/thread** where only team/mods can post, with a monthly digest.

#### Pain Point B: Missing “Start Here” / onboarding link rot (Documentation)
**High impact / Low difficulty**
1) **Add a single canonical entrypoint** (e.g., `docs.elizaos.ai/start-here` or README “Start Here”) that includes:
   - install/run minimal path,
   - contribution path (eliza.army skill),
   - where to ask questions (public channels) and what not to do (no DMs for support).
2) **Discord bot command** (`/start`, `/docs`, `/contribute`) that returns the canonical links and pins.
   - *Comparable pattern:* Next.js and Tailwind communities use command-driven link sharing + pinned “READ THIS FIRST” posts to reduce repeated Qs.
3) **Public “first contribution” issues** linked from the Start Here page (good-first-issue + clear owners).

#### Pain Point C: Scam exposure during support incidents (Security/Community)
**Very high impact / Medium difficulty**
1) **Establish a verified support workflow**:
   - A single “Support” page with rules: “No staff will DM first,” “Only open tickets via X,” “Verify staff badges,” etc.
   - A Discord-only “Support Tickets” bot with locked-down permissions and visible audit trail.
2) **Auto-moderation for scam patterns**:
   - Block/flag messages containing common fake ticket domains/URL shorteners in relevant channels.
   - Rate-limit new accounts posting links.
   - *Comparable pattern:* many crypto-adjacent Discords use AutoMod + link allowlists + “new user link cooldowns.”
3) **Incident playbook**: pinned checklist for missing deposit reports (what details to gather, expected SLA, escalation route).

#### Pain Point D: Token utility confusion (Technical Functionality + Communication)
**Medium impact / Medium difficulty**
1) **Define “token utility” as a technical spec** (even if minimal):
   - What integrations exist today? What APIs/contracts exist? What’s deprecated?
2) **If utility is intentionally community-built**, ship a **reference implementation** (“token utility plugin example”) so “you can add utility” becomes actionable.
   - *Comparable pattern:* Stripe/Shopify ecosystems reduce confusion by shipping “example apps/plugins” as canonical references.
3) Add an FAQ entry: “What is implemented now vs aspirational?” with dates.

#### Pain Point E: Contributor skill & CI friction (Integration/Performance)
**High impact / Medium difficulty**
1) **Fail-fast CI gates for fork PRs** when workflows are `action_required` (issue #17551):
   - Detect GitHub check state and return a clear message: “Awaiting maintainer approval to run workflows: …”
   - Avoid burning 20–40 minutes polling when success is impossible.
2) **Broaden contributor skill compatibility** (issue #17674):
   - Remove `--slurp` reliance; implement pagination compatible with Ubuntu 24.04 packaged `gh`.
   - Document supported `gh` baseline and add a preflight check that prints actionable remediation.
3) **Add “Contributor Experience” CI dashboard**:
   - Track median time-to-green for fork PRs; alert when gates time out disproportionately.

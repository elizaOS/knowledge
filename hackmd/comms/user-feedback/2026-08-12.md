## User Feedback Analysis — 2026-08-12 (based on Aug 9–11 Discord + current GitHub top issues/PRs)

### 1) Pain Point Categorization (Top recurring 5–7)

#### A. Community (Governance / Trust)
1) **Founder commitment + governance uncertainty around the token**
- **Evidence:** Discord discussion (Aug 11) centers on Shaw reportedly selling ~$25M worth of tokens and retaining only ~$40K; multiple users label project a scam; repeated questions about “who controls the token” after “holders went rogue” (Aug 9).
- **Impact:** High severity (trust collapse), high frequency (dominant topic across **3/3** recent Discord daily summaries).
- **Users affected:** Token holders + newcomers evaluating credibility.

2) **MetaDAO transition confusion (is the token being ended?)**
- **Evidence:** Repeated “What does MetaDAO mean for Eliza tokens?” and speculation that ElizaOS becomes “just an open-source engine without tokens.”
- **Impact:** High severity (portfolio + roadmap), high frequency (core thread Aug 11).

#### B. Documentation (Tokenomics / Roadmap Communication)
3) **Unclear token utility, tokenomics, and relationship between open-source framework vs token**
- **Evidence:** Users debating “utility token → memecoin” with no official clarity; repeated “will utilities and use cases come?”
- **Impact:** High severity, high frequency; causes rumor-driven narrative.

#### C. Integration (Exchanges / Market Infrastructure)
4) **Exchange risk + liquidity signaling (Bybit ST tag / delisting fears)**
- **Evidence:** Bybit ST tag (low liquidity warning) and delisting threat repeated; users ask “What happens if Bybit delists?”; exchanges named Bybit/MEXC/KuCoin (Aug 10).
- **Impact:** High severity (access/liquidity), medium frequency but emotionally dominant.

#### D. Technical Functionality (Cloud Provisioning / Reliability)
5) **Cloud agent provisioning regression + long failure feedback loop**
- **Evidence (GitHub #18052):** **16.1% hard failure** since 2026-08-06 (20 failed / 124 jobs trailing 7 days), versus **0/63** the prior 11 days; failure path informs user after **~52 minutes**, and can cause a *permanent lockout* until a fix lands.
- **Impact:** Very high severity; directly blocks onboarding and paid usage.

#### E. Performance (First-run / Login Interactivity)
6) **Login page blocks interaction while waiting on auth providers**
- **Evidence (GitHub #18049):** `/steward/auth/providers` gates sign-in buttons for up to **4.7s** in production; staging also shows multi-second spikes.
- **Impact:** High severity at the top funnel; measurable conversion risk.

#### F. Integration + UX (Connector Onboarding / Identity Binding)
7) **Telegram onboarding is broken and identity doesn’t bind to Cloud account**
- **Evidence (GitHub #17888):** Telegram bot returns onboarding URL to `eliza.app/get-started` which fails to boot reliably; even workaround on `app.elizacloud.ai` doesn’t durably link Telegram identity—second DM re-triggers onboarding instead of routing to the agent.
- **Impact:** High severity for multi-channel agent usage; undermines “agent everywhere” promise.

### 2) Usage Pattern Analysis (Actual vs intended)

**Observed actual usage patterns**
- **Token-first engagement dominates Discord:** Recent Discord feedback is overwhelmingly about token status, governance, and exchange risk rather than framework building (token discussion is the primary topic in **3/3** daily summaries).
- **Real-world vertical agent builds exist but are under-amplified:** A user (0x_cup) reports a **transportation AI agent** successfully built on elizaOS (Aug 10). This indicates the framework is being used for applied operational agents, not just demos.
- **Cloud + connectors are central to user journeys:** GitHub top issues cluster around Cloud provisioning, auth, and connector onboarding—suggesting many users are experiencing elizaOS via **managed Cloud + messaging platforms**, not local-only OSS runtime.

**Mismatch vs intended**
- Intended narrative: “Open-source agent framework + Cloud surfaces.”
- Actual reality for many: “Token governance uncertainty + Cloud onboarding friction.” The technical wins (voice streaming, CI hardening, planner fixes) are not what users are emotionally responding to in community channels.

**Feature requests aligned with usage**
- **Governance structure request:** “Create ElizaDAO with ElizaOS token and 25% fees to foundation” (Discord feature suggestion). Regardless of merits, it reflects a demand for *explicit governance + revenue/utility linkage*.
- **Connector onboarding reliability:** Repeated failures imply users want “connect Telegram/Discord and just work” as a primary product path.

### 3) Implementation Opportunities (2–3 concrete solutions per major pain point)

#### Pain Point 1: Token governance/trust + MetaDAO confusion (Community/Documentation)
**High impact / Low–Medium difficulty**
1) Publish a **single canonical “Token & Governance Status” page** (versioned, dated, changelogged)
- Include: current token controller status, planned governance model, what MetaDAO means *and what it does not mean*, and a decision timeline.
- Similar approach: Ethereum L2 projects frequently maintain “roadmap + governance” pages with explicit “proposed / accepted / implemented” states to reduce rumor cycles.

2) Run a **structured AMA with pre-collected questions** and post a transcript with explicit answers
- Use the top recurring questions from Discord FAQ: Shaw sale details, ST tag implications, token utility direction, MetaDAO impact.
- Make it auditable: link to sources (e.g., CoinDesk interview) and clarify what is verified vs speculation.

**Medium impact / Medium difficulty**
3) Establish a **community governance working group** with scoped authority (information-first)
- Initial remit: document token control, propose transfer steps (aligns with zadayos guidance: new legal entity + work with Shaw).
- Similar model: many OSS projects create “steering council” or “governance RFC” process before implementing on-chain governance.

#### Pain Point 2: Cloud provisioning regression + 52-minute failure feedback (Technical Functionality)
**High impact / Medium difficulty**
1) Implement **fail-fast user feedback** for provisioning
- If capacity/autoscaler/fence deadlock conditions detected, notify user within minutes, not 52 minutes.
- Add explicit error classes (capacity, autoscaler ceiling, fence deadlock) with remediation hints.

2) Add **auto-remediation and guardrails** around the three suspected contributors (#18052)
- Autoscaler: make `maxNodes` configurable (and validated against enabled nodes).
- Fence deadlock: detect “stranded fence” and trigger retirement/cleanup workflow.
- Capacity accounting: enforce consistent slot accounting and prevent oversubscription drift.

**High impact / Higher difficulty**
3) Add a **provisioning SLO dashboard + regression alerting**
- Track daily failure rate, p50/p95 provision time, and “time-to-user-notification.”
- Similar approach: Kubernetes operators and serverless platforms use SLO-based paging to catch exactly these “dated regressions.”

#### Pain Point 3: Login interactivity gated by slow `/steward/auth/providers` (Performance)
**High impact / Low–Medium difficulty**
1) Cache the providers response (with safe invalidation)
- If enabled providers change only at deploy/config time, cache with TTL + purge on deploy.
- Similar approach: NextAuth-style provider lists are often static; caching eliminates cold spikes.

2) Render sign-in options optimistically with a fallback
- Ship a default set of buttons immediately; hide/disable only if the endpoint says unavailable.
- Ensure safety: don’t present providers that are disabled, but avoid blocking UI for seconds.

#### Pain Point 4: Telegram onboarding + identity binding fails (Integration + UX)
**High impact / Medium difficulty**
1) Fix canonical onboarding host and asset MIME consistency
- Ensure `ELIZA_ONBOARDING_APP_URL` points to a working host; enforce correct content-type and cache behavior (the reported `text/html` module mismatch is a classic CDN fallback/cache misconfiguration).

2) Add **server-validated Telegram proof** before linking identity
- Implement Telegram Login/OAuth verification or signed payload validation server-side.
- Similar approach: Slack/Discord account linking flows require signed callbacks and nonce-binding; browser auth alone is insufficient.

3) Add connector E2E tests that explicitly prove “DM → link → DM routes to agent”
- Include negative cases (expired token, replay, mismatch) as specified in #17888 acceptance criteria.

#### Pain Point 5: Exchange ST/delisting fears (Integration + Communication)
**High impact / Low difficulty**
1) Publish a **“What ST tag means / delisting risk / what we can and can’t do”** explainer
- Include practical guidance (where to check liquidity, what official comms channels are, what timelines look like).
- This reduces panic loops even if the underlying market issue remains.

2) Clarify whether token is *required* for framework usage and what continues regardless
- Explicitly separate: OSS framework health vs token market health.

1) **Expectation:** Token has clear utility and aligned incentives

   **Fix:** publish utility roadmap (or explicit deprecation plan) with dates and decision points.
